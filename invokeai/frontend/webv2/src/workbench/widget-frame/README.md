# Widget placement, focus, and windows

Paths are relative to the webv2 `src/` directory.

Placement: `workbench/floatingWindows.ts`; focus: `workbench/focusRegions.tsx`; shortcut hints: `workbench/hotkeys/`; window chrome: `workbench/widget-frame/`.

## Placement and floating windows

What a project shows is computed, never stored: its workspace's **structure** (account-owned: which instances sit in which region, in what order, which float, each region's home front, default sizes, collapsed panels and window geometry; `workbench/workspace/structure.ts`) seen through the project's **view** of that workspace (`Project.views[workspaceId]`: sparse overrides of fronts, sizes, collapsed panels and window geometry, and its guests; `workbench/workspace/view.ts`). Only Customize, or a structural gesture with **Rearrange without Customize** on, writes structure, for every project on the workspace; everything else (fronting, collapsing, resizing, moving a window, entering, navigating, Reset view) writes the active project's view only. An override equal to its default is not stored, except a side region's front of an instance it shares with the center, which records the explicit ask repair 4 honours. The account's workspaces have one owner, `workbench/workspace/accountWorkspaces.ts`: it reads and writes a workspace's structure and its name, icon and route (a built-in's override goes whenever what it would store, or what load reads from it once retired widgets are stripped, equals what the built-in ships, so it follows later releases; every structure it writes is noted as the workspace model's, which adoption never replaces, see [projects/README.md](../projects/README.md#workspaces-and-views)), and reads and puts back everything the account holds for one workspace (`WorkspaceRecord`), which layout undo uses. `resolveLayout` (`workbench/workspace/resolveLayout.ts`) turns the two and the registry's availability into the `ResolvedLayout` the shell reads (`widgetRegions`, `floatingWidgets`, `panels`, instance identity, `guests`); it is pure, total and idempotent, and its repairs are listed beside it. While a project customizes, the structure is its Customize draft, and a new workspace's draft is seen through the view kept under the id Done will create it with (`getProjectViewId`). The store owns one memoized resolver per open project (`createLayoutResolver`, dropped when the project closes) and the availability (rebuilt only when the session's admin flag changes); the snapshot carries the active project's `activeLayout`, `useActiveLayoutSelector` selects from it, `queries.getWorkspaceLayout` answers for the active project's other workspaces, and `queries.getAvailability` hands the shell the same availability. The reducer resolves through `WorkbenchReducerContext.availability`, so it reads no registry.

Placement rules (`workbench/floatingWindows.ts`, `workbench/workspace/structureReducer.ts`):

- **A floating instance belongs to no region's `instanceIds`.** Floating removes every membership, repairs home fronts it leaves behind, and records one return destination (`returnRegion`, `returnIndex`) and every other region it left (`alsoIn`: its position among that region's docked members and whether it was the front, as Preview is in Edit's center and right rail). Docking puts it back in each, so floating a shared instance and docking it never costs another region its view; closing a window removes it from the workspace. `alsoIn` is optional and additive: a build that predates it reads the window and docks it to its return region only.
- **Any widget a side region holds can float.** There is no per-widget opt-in: a panel's Float Window button, and for a widget without a header (Layers) its rail tab's context menu, float it while structure is editable, unless that would take the center's last view.
- **A return region keeps a marker for each of its windows.** `getRegionOrder` is region's complete order (docked members plus markers); a marker's `returnIndex` is its position in it. Docking counts docked members ahead of marker, so docking in any order never moves what rail shows. Structural edits that add, remove, or move members go through that order so indices stay in step; reordering docked members fills docked positions around stationary markers.
- **The center keeps a view.** `takesLastCenterView` (`structureReducer.ts`) is the one definition, by the session's availability (an admin-only view a non-admin session cannot show does not count): `reduceStructure` refuses an edit that would take the center's last member or last view, and the shell asks the same predicate, so a frame offers no Float Window, the center view menu no Close, and the Widgets list marks the view required. `normalizeStructure` docks a stored structure's floated-away last center view (the window the center fronted, else the first returning there), so no loaded structure leaves the center empty for a window. A structure whose center shows nothing available shows the default workspace's stage as a guest instead (`resolveLayout`, repair 3).
- **An instance is shown once**, unless the widget renders a distinct surface in each region (a workflow's graph in the center and its form in a rail: `graphBearing.surfaces`). The stage wins by default: when neither region's front is an explicit view override, the center keeps it and the side region shows its next member, or collapses. An explicit front in the view wins over a home front: an open side panel the view fronts it in keeps it and the center shows its next view; with no other view both show it, so the center is never empty. Between two explicit fronts the latest ask wins, because the writes never leave both: fronting it in a side panel drops the view's center front of it and fronting it in the center drops every side front of it. One predicate says when an instance shows once (`showsOnceWithCenter` / `isSharedWithCenter` in `workbench/workspace/view.ts`) and one writer makes the ask (`frontRegion`, also there); repair 4, entry and `captureLayout` read the same predicate. The repair itself is display only (`resolveLayout`, repair 4).
- **Region requests never discard a window.** Selecting, moving, or reordering an instance a region does not hold is a no-op; so is enabling an instance that floats. A structural add of a widget type with a window docks that window back first.
- **Values belong to the project, placement to the workspace.** `Project.widgetInstances` holds each instance's values by id; every instance the active project's workspace places gets a record when the project meets that structure (activation, a switch, a structural edit, Done), and one a structure stops placing keeps its values for when it is placed again. Instance titles are the structure's.
- **Layout history is undoable, layout only.** Customize starts and ends on an empty history and keeps its own while it lasts (see [Lock and Customize](#lock-and-customize)). Outside it, every layout step the user makes is one project undo step: opening, adding or removing a widget, floating, docking or closing a window, moving or reordering a tab, alignment, collapsing a panel, a window's mode, workspace switches, route changes and Reset view. A dragged divider or moved window folds into one step per region or window (same key within 1.5 s); raising a window, selecting a tab, fronting what an open shows, or going home on the active workspace is navigation, not a step. A step snapshots the project's workspace, views, route and instances; undoing it restores them while every widget keeps its current values. A step that changed a workspace in the account (a structural gesture while rearranging without Customize, or Customize's Done) also records what the account held for that workspace before and after it; undoing it puts the before back for every project on the workspace, but only while the account still holds the after. When something changed the workspace since (another project, Customize, deleting it), the step still puts back this project's own view and route, leaves the workspace as it is, and a notice says so; redo follows the same rule. Undo never puts a project back on a workspace the account no longer has, nor gives it a view of one. A step carrying a `LayoutUndoNotice` (switch workspace, remove widget, Reset view, workspace updated) reports itself through `shell/LayoutUndoNotices.tsx` with an Undo toast, withdrawn as soon as that step stops being the project's latest; `app.undoLayoutChange` and `app.redoLayoutChange` step one at a time. History is session-only, at most 40 steps, never persisted.
- **One list of every widget.** The Widgets dialog (`shell/WidgetsDialog.tsx`), opened from the app menu, the foot of each rail's and the status bar's widget menu, the Customize bar and the palette's "Show widgets", lists every widget placed in this workspace (with where: a rail, the center, the status bar, a window) and every one it lacks, with Show, and Add, Dock and Remove while structure is editable; locked, its footer offers Customize instead, which keeps the dialog open. A guest is listed as a widget the workspace lacks. While structure is editable, a placed widget whose `needs` the workspace does not place says so beside where it is: advice, never a block. The palette also has a Show entry per widget. The dialog describes this workspace, so its Show never leaves it: one the workspace lacks shows as a guest. Show closes the dialog and moves focus to the widget; the other actions keep it open and keep focus on that widget's row; closing it otherwise returns focus to the control that opened it, or the app menu trigger when that control is gone.
- **One normalization.** `normalizeFloatingPlacement` runs inside `normalizeStructure` on every stored or imported structure and on layouts stored before structure and view split. Idempotent. Indices stored before markers were counted are read deterministically (ascending, ties by instance id, missing ones appended); best-effort, does not reconstruct original arrangement.

- **A closed window leaves its geometry behind.** When a window the project shows closes (docked, removed, or closed by an undo), its position and size as shown move to `Project.lastFloatingGeometry` (`rememberClosedWindows`); floating the instance again takes them back out and reopens the window there, windowed; only a first float cascades. Float command passes viewport, so a rectangle remembered in a larger one is brought wholly on screen, not reopened as a sliver. Memory holds only instances that exist; persisted with the project and validated on load, but not layout: undo snapshots do not carry it.

Rails subscribe to placement only (`getWidgetPlacementProject` projects `floatingPlacements` from the resolved layout), so a window's geometry, mode, and stacking change without re-rendering them. A marker is not a tab: it stays out of sortable list, activating it raises and expands its window, and its context menu offers Dock and Remove (the window's own title bar has both too). Marker UI exists only on left and right rails.

## Opening and workspaces

A workspace is a layout preset (code keeps the `LayoutPreset*` names and stored fields); what switching to it shows for this project is its structure seen through the project's view of it (`queries.getWorkspaceLayout`). Every open, show, send-to and recall states an intent, never a region: `OpenIntent` (`workbench/workspace/openIntent.ts`) names a widget type and, optionally, `surface: 'stage'` (only a center view serves) or `'panel'` (a rail, the status bar's panel, or a window; a tooltip or popover chip never does). `openInWorkspace` (`workbench/workspace/workspaceNavigation.ts`) asks the pure `resolveOpen` and turns its answer into view commands. Widgets reach it through `runtime.workbench.open`.

- **First match wins.** 1. On screen here (the center's fronted view, the fronted tab of an open, expanded panel, a window, or a status-bar or toolbar chip): focus it; a window is raised and expanded. A region shows its front even when the center fronts the same instance (a workflow's graph in the center and its form in a rail), so such a rail copy counts as on screen; only opening or fronting in the center hands a rail to its neighbour. 2. Placed here but hidden: front it, preferring a region that already fronts it, then right, left, status bar, and the center last. 3. Placed in another workspace: enter the one where it is the stage, else the job's source, else a home front, else placed at all, ties in tab order; another workspace's guests do not count, and a widget with `needs` only considers workspaces that place what it needs. 4. Placed nowhere this open may go (no workspace, or none it may enter: `'stay'` mode and Customize resolve with steps 1, 2 and 4): show it here as a [guest](#guests), in the center (Away) for the stage or a widget only the center shows, else in a window. A type that is disabled, hidden, admin-only, or cannot take the asked surface is unavailable, and so is a status-bar chip placed nowhere: no surface outside the status bar shows one. No gesture answers "not placed".
- **Navigation writes view only.** It fronts (`widgets.front`, which never adds a member), expands and opens panels, raises windows, and shows guests. Adding, moving, floating, docking and removing belong to the shell's structural controls (the rails', status bar's and center's add menus, the Widgets dialog) and a guest's **Keep in workspace**.
- **One gesture crosses at most one workspace.** Of several intents (find in gallery: Preview, then Gallery), only the first may enter another workspace; the rest resolve against the workspace it lands in, without leaving it, and still show when the first is unavailable. Entering flushes drafts and goes through `layout.activatePreset`, so a cold workspace loads within its deadline and a superseded entry fronts nothing. The switch is the usual undoable step with its "Switched to" toast.
- **Work after the open waits for it.** What needs the widget on screen (setting the route to it, focusing a field in it, revealing an issue or node) goes in `afterShown`, which runs in the same task when the widget shows here, once a cold entry lands, and never when the entry is dropped or nothing showed. Values the action writes land at once: they belong to the project, not the layout.
- **Back to previous workspace** (palette, assignable hotkey) returns to the workspace this project's last navigation left, seen through the project's view of it and entered, while the project is still where that navigation took it. Any later switch, by tab, shortcut or Undo, forgets it, so Back never returns somewhere the user has since left by hand. The memory is session-only, per project, and cleared with the account.
- **Only gestures navigate.** A gesture moves workbench focus to what it showed: its first intent's widget, or the one it names (find in gallery focuses the Gallery). A background source such as a socket recall passes `background`: it fronts only what this workspace places, moves no focus, shows no guest and records nothing itself; its own notice carries **Open** (`withRecallWidgetOffer`), the gesture that may navigate. Toggle Preview and Switch workflow view never leave the workspace; what they lack shows as a guest: Preview in the center, the workflow's graph in the center, its form in a guest window (`openGuest`, since the resolver would answer a panel ask with the graph in the status bar's panel).

### Guests

A guest is a widget this workspace does not place on the surface it is shown on, shown by this project: view, not structure. `WorkspaceView.guests` records each by instance with its type and surface (`'center'` or `'window'`); a guest window's geometry, mode and stacking are its entry in `view.windows`, whole since it has no structure default. `resolveLayout` composes them: a center guest is fronted in the center, so the center is Away ("Back to {stage}", Escape); a guest window is a window among `floatingWidgets`, returning to no region (no rail marks it; `floatingPlacements` leaves it out). `ResolvedLayout.guests` names every guest shown, the center's fallback stage (repair 3) included, and the shell reads it; widgets never know they are guests.

- **One per type.** A guest is one of the project's own instances of its type that this workspace's structure does not use: the one named after the type first (the instance graph builders and recall read by type), then the project's others in id order (`getGuestInstanceId`). Only when the workspace uses all of them, as when it places the type on another surface, is the guest a new instance, `{type}:guest`, with the type's initial values and values of its own from then on. A guest the view already shows for the type is shown again, so opening it twice focuses it, and its values survive closing it. A view holds at most one guest per type and one in the center (a new center guest replaces it); `MAX_GUESTS` (12) bounds what a stored view loads.
- **Lifetime.** Guests belong to that workspace's view: leaving the workspace hides them, returning shows them, they are saved with the project, and Reset view and deleting the workspace drop them. Closing a guest forgets it and keeps its window's geometry for next time (`lastFloatingGeometry`). A center guest is forgotten whenever the center fronts something else (Back to stage, entry, picking a view): `frontRegion` on the center drops it. One predicate, `isGuestSuperseded`, says when the structure supersedes a guest: it uses the guest's instance id, or shows its type where the guest does (a placement repair 1 hides, where the type cannot show, does not count), which is the center for a center guest and, for a guest window, any side region or window showing the same surface (for a type with a surface per region, `graphBearing.surfaces`, only those of the region the window stands for: a workflow's form window is not its graph in the status bar's panel). `resolveLayout` then shows the placed one instead (repair 5), `pruneView` forgets the guest and `showGuest` does not open one, so removing that placement later brings nothing back. A guest window showing the fallback stage's instance keeps it, and the center shows no fallback (repair 3).
- **Chrome.** A guest window's title bar has **Keep in workspace**, Collapse, Maximize and Close, and no Dock; a center guest has Keep in workspace and Close in the center view menu (Close only while the center has a view of its own). The center's fallback stage (repair 3) is a center guest like any other, so Keep places it and, with nothing else to show, it has no Close; where a rail places the stage's own instance, the guest is another of its type, so a guest is never a placed instance. `getShownGuest` (`resolveLayout.ts`) is the one judge of what a shown guest offers: the shell reads it, and the reducer's `keepGuest` and `closeGuest` refuse what it does not allow. Locked or not, guests work.
- **Keep in workspace** (`keepGuestInWorkspace`) places the guest's own instance, the one above with its values, on its surface: a center guest as a center view, fronted; a guest window as a placed window returning to the side region it stands for (the first of left, right, bottom that shows the type as a panel), at its geometry, so what is on screen does not move. Locked, it enters Customize with the widget added to the draft: Done places it, Cancel leaves it a guest. With Rearrange without Customize on it writes the workspace, as other structural gestures do.
- **While customizing.** Navigation shows guests as usual; they are not part of the draft, and Done does not capture them into structure.

### Needs

A widget whose manifest declares `needs` (the types it acts on: Layers needs Canvas) shows a one-line notice in its frame while one of them is not on screen and the widget itself is: "{Canvas} is hidden · Show Canvas" when this workspace places it, "{Canvas} is not in this workspace · Show Canvas" when it does not. On screen is the center's front, each open side panel's front, and every window not shaded (`getUnmetNeed`, `workbench/workspace/unmetNeeds.ts`); a need this session cannot show at all says nothing. The action is a gesture through the resolver, so it fronts the need here, enters the workspace that has it, or shows it as a guest. The shell draws the notice (`UnmetNeedNotice`): a compact strip at the foot of a side panel's, window's or center view's body, so the body gets shorter and what the user works with at its top does not move; it truncates its text before its button and is announced once through a polite live region. The widget renders as usual and contains no check.

### Entering a workspace

Every entry applies one rule, `enterWorkspace` (`workbench/workspace/entry.ts`), a pure function over the workspace's structure, the project's view of it and the workspace's saved definition. Stage and job are read by `workbench/workspace/workspaceDerivations.ts`.

- **The rule.** The center fronts the **stage**, the center's home front in the structure (`getWorkspaceStage`; what a center shows now is `getCenterFront`, a different fact): entry fronts it there with `frontRegion`, the same ask a gesture makes, so the view's center front goes and so does a side region's explicit front of the stage's own instance: the stage is in the center after every entry; `resolveLayout` shows the first available center view when the stage cannot render. The **job**'s source is fronted in its side region: the saved home front where it is still placed, else the first rail or status-bar instance that runs it. The route becomes the job, source and destination locks each kept. It writes the view's fronts and the route only: never structure, sizes, collapsed panels, other regions' fronts or windows, so a collapsed panel stays collapsed with the source fronted in it, and a run or staged canvas result in flight is untouched.
- **The job** derives from the structure: a guest, the fallback stage included, is shown but not placed (`isPlacedInstance`, the one predicate `resolveOpen`, the Widgets list, the center's view count, needs, window markers and window chrome share), so it never makes a source placed or names the job. It is the explicit `defaultRoute` while its source is placed, else the first placed source among the saved home fronts in the order center, left, right, bottom (then the laid-out ones), to its natural destination. A workspace with no source has no job, and entry leaves the route as it was.
- **Entries.** Switching by tab, Alt+1…4, the palette, navigation (`openInWorkspace` enters, then fronts the requested widget and runs `afterShown`) and Back to previous workspace; a Launchpad intent (it enters, then shows and aims at its own source when that is not the job, as Upscale in Compose); and a project's first activation in the editor session (hydration, open, or first switch to it: `WorkbenchState.enteredProjectIds`, transient). Returning to a project already active this session shows what it was left on.
- **Going home.** Choosing the active preset (its tab, its shortcut, the palette) runs the same rule over the project's view: no undo step, no notice. The store applies it without the cold-load activator, and it drops a pending switch.
- **Reset view.** A workspace tab's menu (active or not, locked or not) and the palette's `app.resetWorkspaceView` (for the active workspace; unavailable while customizing) drop the active project's view of that workspace (`resetWorkspaceView`), so every front, size, collapsed panel and window is the structure's default. One undo step, reported with an Undo toast; the menu item is unavailable, with its reason, and the palette leaves the command out, while the project has no view of that workspace.
- **Away.** The center fronts a view other than the stage, while the stage is placed there (`getAwayStage`). No extra state: entry ends it. The center header's start island then leads with **Back to {stage}**, which fronts the stage and moves focus into the center (`goBackToStage`); with no stage placed in the center there is no marker. `app.backToStage` (Escape) does the same with the center focused. It is a `fallback` binding: below every other scope, global included, and run only after the press has reached every listener and only when none marked it used (`defaultPrevented`). Waiting matters because the Canvas engine also listens on `window` and can come after the hotkey runtime. So a text field, an open menu or popover (Zag marks the Escape it dismisses with), a widget's own Escape binding (Preview's comparison, Image Map's selection), a Canvas Escape that cancelled something and a workflow editor Escape that unselected a focused node or edge all keep it; a Canvas or editor with nothing to cancel lets it go back. A handler that consumes Escape marks it with `preventDefault`.
- **Toggle Preview (Z)** swaps Preview into the center (Away) and back to the stage. Where Preview is the stage, it swaps to the center's first other view and back; where the center does not place it, Preview shows as the center's guest.

## Lock and Customize

Structure, which widgets sit where and the workspaces themselves, changes only in **Customize**; view changes are free everywhere. `workbench/workspace/structureLock.ts` is the one judge (with the session contracts and `pruneCustomizeSessions`): structure is editable while the active project customizes the workspace it is on, or everywhere for an account with **Rearrange without Customize** on (`WorkbenchPreferences.rearrangeWithoutCustomize`, see [settings](../settings/README.md)). The shell reads it through `useStructureLock` / `useCanEditStructure` (`workspace/useStructureLock.ts`); widgets never do, because every structural control is shell chrome.

| Change                                                                                                                                    | Kind                 |
| ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Front a tab, switch the center view, collapse or resize a panel, move, resize, shade or maximize a window, show or close a guest          | View: always allowed |
| Add or remove a widget, move it between regions, reorder tabs, change status-bar alignment, float or dock a placed widget, close a window | Structure            |
| Create, rename, reorder or delete a workspace, set its icon or route                                                                      | Structure            |

- **Locked means not offered.** The rails' and status bar's widget menus and their context menus (Remove, Dock, alignment), the center view menu's add group and Close, a panel's Float, a placed window's Dock and Close, the Widgets dialog's Add, Dock and Remove, and the workspace tab menu's Delete are not rendered. Locked, the tab menus have two explicit doors into structure and nothing that edits it directly: **Customize** in the active tab's menu (this workspace, as a draft; another tab's menu offers switching to it instead) and **Manage workspaces** in every tab's menu (the set: order, deleting one, a built-in's default, each after its confirmation; it applies at once and is not offered while customizing). Unlocked, the same menu adds Delete, and the strip's tabs drag to reorder. Drag handles take no listeners and announce no sortable role (`useWidgetSortable`, the tab strip's `useSortable`), so no drop target ever activates. The reducer has no mode: a structural action edits the Customize draft while the project customizes, else the workspace in the account, and only these boundaries gate it.
- **Customize is a draft.** `WorkbenchState.customizing` maps a project to its session (`CustomizeSession` in `workspace/structureLock.ts`; every transition, its history and what Done writes are pure functions in `workspace/customizeDraft.ts`, which the reducer calls): the workspace it is on (`presetId`), a draft structure, a draft of the name, icon and route (`draft`; absent fields are the base's), a pending reset (`resetPending`), for a new workspace's draft the id Done creates it with (`newWorkspaceId`), the account's structure and the project's view and route when it began (`entryStructure`, `entryView`, `entryRoute`), where its own auto-routing last left the route (`routeLeft`), and its own Undo and Redo history (at most 40 steps). Nothing in the draft reaches the account until Done: structural gestures, name, icon and route edits, Reset to default, New workspace and Save as new all change the session only, and the project's view while customizing is the session's working view. Managing the workspaces (order, deleting one, another built-in's default) is not part of a draft: the Manage dialog applies each change at once, and Customize does not offer it, since Cancel could not take it back. Transient like `enteredProjectIds`: never persisted, synced or undone, emptied by hydration and cleared with the account. A session ends with its workspace: when the project closes or leaves that workspace, or the workspace is deleted, the reducer drops it (`pruneCustomizeSessions`); a session that ends so while its project stays open, with an arrangement, reset or metadata edit to lose (`hasCustomizeChanges`; view changes stay with the project), says so in a "Customize ended" notice that names why: the workspace was deleted, or the project moved off it. Switching projects keeps it, so returning shows it again.
- **Its history covers every edit.** Each structural gesture, view change, name, icon or route edit (typing a name folds into one step per burst) and Reset to default is one session step; Undo and Redo in the bar and the layout undo commands step the draft, its metadata, the reset flag and the view together. Customize puts back only what its own auto-routing moved: a step records the source and destination its layout action's auto-routing moved (`RouteMove`, never the locks), and Undo or Redo moves the route back or forward only while it is still where that step left it; a route or lock picked by hand is no step and stays.
- **Entering.** The active tab's menu, the app menu, the palette and an assignable hotkey (`app.customizeWorkspace`), a locked hint's Customize, and a guest's Keep in workspace (with the widget already added). `startCustomizing` (`workspace/workspaceNavigation.ts`) records, per project, where focus returns and what in the bar takes it. Beginning drops a workspace switch still loading (it would land on another workspace and end the session) and clears the project's layout history. **New workspace** (the strip's +, available while locked; `customizeNewWorkspace`) begins a session on a draft of a workspace that does not exist yet: its structure is the current workspace's with what is on screen taken as its defaults (`captureLayout`), seen through an empty view of its own, its name a unique "{name} copy" in the focused name field. The project's views of existing workspaces are untouched.
- **The bar** (`shell/topbar/CustomizeBar.tsx`, loaded on first use) replaces the workspace tabs: name, icon (`LayoutPresetIconPicker`), route (`LayoutPresetRouteFields`: Auto where the workspace may have none, otherwise a source it places; a built-in always has its shipped route, so it has no Auto), Undo and Redo, Widgets, Reset to default, Save as new, Cancel and Done. The bar only dispatches: what the absent draft fields read as has one owner (`getCustomizeBase`: the built-in as shipped while a reset is pending, else as saved), and a built-in's shipped name typed in the reader's language is stored as the shipped one. **Reset to default** is offered while a built-in's draft differs from what it ships with (`createShippedStructureSelector`, recomputed only when the draft, view or layout changes, and the name, icon and route), whatever the account holds: it makes the draft the shipped structure and metadata seen through an empty view, and marks the reset pending; Undo withdraws it. **Save as new** (not offered on a new workspace's draft) turns the session into a new workspace's draft carrying the arrangement and view so far, with a unique copy name in the focused name field; the original workspace and this project's view of it are as they were before Customize. A narrow window scrolls the editing controls sideways behind the overflow cues the center chrome uses (`shell/overflowEdges.tsx`); Cancel and Done stay in view.
- **Done** (`finishCustomize`, one reducer step, computed from the session alone by `finishCustomizeSession`) takes what is on screen as the draft's defaults (`captureLayout`: each region's front its home front, the center's the stage, where repair 4 moved the center the view it showed instead, and the sizes, collapsed panels and window geometry). For a new workspace's draft it creates the workspace, last in the tab order, and moves the project onto it. Otherwise it removes a built-in's overrides when a reset is pending, writes the structure only where it differs from what the account holds (a built-in back at its shipped structure loses its override) with the name, icon and route, and a session that changed nothing writes nothing, so an untouched built-in is never pinned to this release's arrangement. Done writes only its own workspace's entries. The project's view of the workspace keeps only what those defaults cannot say (`pruneView`). On an existing workspace that changed, Done is one step of the project's layout history, back to before Customize (its view included, and the route by the same rule as Cancel, only while the workspace goes back too), with a "{workspace} updated" Undo toast, under the staleness rule above; a new workspace's Done is none (Manage deletes it). **Cancel** drops the session and its draft view: the account and the project are as before Customize, and the route goes back to where it was only while it is where the session's auto-routing last left it (`getCustomizeRouteReturn`); a session that never moved it, or a pick by hand since, leaves it. Both start the layout history afresh, Done with its own step. However a session ends while its project is on screen (Done, Cancel, its workspace deleted), focus returns to the control that opened it while that is on the page, else to the active workspace's tab. Closing the Manage dialog returns focus to the tab whose menu opened it, or to the active tab when that one is gone. Entering by a gesture moves focus to the bar, or for a new workspace's draft to its name; Escape there does nothing destructive.
- **Navigation stays inside.** While customizing, `openInWorkspace` resolves in `'stay'` mode (steps 1, 2 and 4), `layout.activatePreset` refuses another workspace, and the workspace-switching commands and Back are unavailable. The app stays live: Invoke and everything else keep working.
- **The center keeps a view.** Customize does not offer to remove or float its last one (`takesLastCenterView`, above); Reset to default, Undo, Redo, New workspace and Save as new only ever restore or copy a structure that kept one.
- **Rearranging without Customize** makes every structural control work in normal use: each gesture writes the workspace in the account at once, for every project on it, and is undoable; Customize stays available. Nothing anywhere reads as unsaved: view changes are remembered per project as they happen, and structure is the account's. Turning the setting off clears the layout history of every project outside Customize (`workspace/workspaceLockRuntime.ts`), so a locked undo cannot bring back a structural step.

## Focus

Workbench focus is transient, never persisted. `WorkbenchFocusProvider` (`workbench/WorkbenchRuntime.tsx`) owns one controller (`workbench/focusRegions.tsx`) above UI ports, hotkey runtime, and shell; no module-level focus state. Target is a docked region or one floating instance.

- **Keyboard navigation.** `Alt+Shift+Arrow` (`Ctrl+Cmd+Arrow` on macOS, where Option+Shift+Arrow selects text by word or paragraph, Ctrl+Arrow chords belong to Mission Control, and Ctrl+Option+Arrow is VoiceOver's navigation chord) moves focus to nearest visible docked region in that direction, using current frame geometry and preferring alignment; with no current target it enters center. Preserves widget selections, skips hidden regions, stops at edge. From a floating window, its center is starting point on movement axis so overlapping docks stay reachable; when no dock lies beyond it in that direction, focus returns to dock under its center. `Alt+PageUp` and `Alt+PageDown` cycle focused docked region's enabled panel views in placement order, wrapping at either end and focusing owning region once selected instance is visible. Side frames wait for their lazy view to load; persistent center frame can take focus immediately. Toolbar, tooltip, popover, and floating placements excluded; a single eligible widget stays open. All six commands are customizable in Hotkeys settings, work from editable fields (defaults are chords no text field binds on that platform), and respect modal suspension. Ordinary Tab and arrow-key handling unchanged.

- **One judge of the target.** `getTarget()` returns target only while it describes something on screen: set under current project and account, and (for a window) still floating. Provider also clears eagerly when active project changes, account changes, or workbench unmounts; that notifies subscribers and abandons a focus move still waiting for its widget to mount. Returning to a project never brings old focus back.
- **Activation.** Pointer-down and keyboard focus activate a region or window; hover does not. Active window carries the same accent outline, under the same preference, as a focused region; no region is outlined while a window is active. Window passes project id it was rendered for, so a late event from a project that left screen is refused before it can raise anything.
- **Raising.** A press inside a window always asks reducer to raise it (no-op for topmost window). Focus raises a window only when it makes that window the active one: focus moving inside already-active window, or returning from a closing dialog or popover, writes nothing. Ordinary focus leaves a shaded window shaded; explicit reveal (marker, center "Show window", recall) expands it.
- **Recall is the one reveal that moves no focus.** Recall raises and expands its window but leaves keyboard focus, outline, and hotkey target where user had them; next press or focus change brings them back into agreement. Since focus inside active window does not re-raise, it cannot re-bury the window a recall just revealed.
- **Keys follow the outline.** A press inside a window moves keyboard focus into it when focus was elsewhere; a press on a docked region pulls focus out of a floating window. Floating layer renders windows in fixed DOM order and stacks them by z-index alone: raising a window never moves its node, which would drop the focus that raised it.
- **Focus follows placement:** into window after Float and after a marker or "Show window" reveal; into the region a docked rail tab shows in when it is selected, so keys stop going to a window that held them; into return region after Dock; after Remove from a marker's menu, into center when it gets its view back, else into the panel the window's own rail is showing, or center when that rail shows none (emptied by float or collapsed). Removing a window from a rail's enable menu moves no focus: that menu stays open and keeps it. A focus move targets region frame on screen (side regions keep earlier panels mounted but hidden), waits a bounded time for its widget to mount, and is abandoned if user presses elsewhere first. A newer modal opening cancels an older waiting or settling move, so that move cannot steal focus during the modal’s close. A move requested while an existing dialog closes remains valid; closing releases presence without starting a new modal generation. Every panel frame carries its instance's identity, including stand-in for a widget whose view cannot render, so a move into it lands.
- **Hotkeys read the same target.** `HotkeyContext.focusedRegion` is `WidgetRegion | 'floating' | null`; persisted `WidgetRegion` unchanged. A key press is aimed at widget under event target first and, outside any widget's DOM, at active floating instance or focused region's active member (`resolveHotkeyTarget`). A region's active pointer counts only while it names a member, so a floating view answers as a window, not as the region it returns to. Floating command source carries `region: 'floating'` and is never used to index `widgetRegions`. Generic `focused-region` shortcuts match under a window, shortcuts tied to a named docked region do not, and a floating widget's own `focused-region` contribution follows its window at the same priority it has when docked. A binding with a `targetSelector` (prompt weighting: an editable prompt whose model reads attention syntax) is a candidate only while the key press's target matches it; elsewhere the next candidate wins, or nothing claims the key and it keeps its browser behavior. Canvas engine's own keys (Enter, Escape, C, and the Space and Alt holds) ask the same judge with the same inputs: the canvas surface maps the target to this canvas, a companion Layers widget, or elsewhere.
- **Modal dialogs suspend application shortcuts.** Every dialog is built on Platform `Dialog` root (`platform/ui/Dialog.tsx`; lint rejects Chakra's dialog and its drawer, which has no such root yet), which registers with `platform/ui/modalPresence` while its own open state holds, unless declared `modal={false}`. A dialog whose module is still loading uses `Dialog.Pending` as suspense fallback, so it is modal from keypress that opened it. While any registration stands, hotkey runtime runs only hotkeys marked `allowInModal` (command palette toggle), so invoke, global and widget shortcuts stay inactive wherever focus is, and keys the dialog handles itself (Enter, Escape, typing) keep browser behavior; Canvas engine's own key listener takes no key either. Both ask about the key press they are handling: a press that began under a modal still counts as aimed at it, because the Escape that dismisses a dialog releases its presence before the same press reaches bubble-phase listeners. Presence follows interactivity, not DOM: a closing dialog that stays mounted through its exit animation is inert and releases at close, so next press reaches application; reopening re-registers at once, an outer dialog stays registered while an inner one closes, and an unmount releases without a close. Media paste reads the same presence. Popovers and menus do not register.

## Contextual shortcut guidance

Shortcuts is a bottom-only popover widget. Built-in layouts put it on right immediately before Notifications; saved and custom layouts keep their placements and can enable it from the Status bar widgets menu. Whole chip opens its guide; normal widget controls own reordering, alignment, visibility and dismissal. Its `compactSizing` metadata asks status-bar host for remaining capacity: host observes its strip, two clusters and spacer; guide measures only its own keycaps. Up to four whole hints fit without increasing status bar height; a keyboard icon keeps access when no hint or label fits. Status-bar chips take their accessible name from compact content, never a host `aria-label`, so speech-input users can say the status they see (WCAG 2.5.3 Label in Name). Once its view loads (until then its busy fallback reads "Loading <label>"), every chip's name starts with its widget's label: a compact view whose status text does not say it ("Queue idle", a workflow's name) passes `StatusWidgetChip` a `hiddenLabel` or renders the label visually hidden. The guide's name is only "Shortcuts": its preview hints are `aria-hidden`, so a voice command for a hint cannot land on the chip, and the popover lists them. The `workbench-status-bar-names` accessibility journey enables every bottom widget and checks each chip's name. If all relevant bindings are unassigned, popover explains that state and provides keyboard shortcut settings.

Workbench focus lifecycle also owns transient hint-source registry and last editing element. A keyed Canvas registration mounts one stable source for its project/instance engine lease. Generation and staged results never change Canvas hints: nothing locks the canvas. Narrow tool/session subscriptions cache scalar hint inputs; guide never acquires an engine lease or imports property forms. Sources are fenced by project and instance and released with their owner. Project/account changes clear editing origin. Widget's `preserveWorkbenchFocus` metadata keeps its compact chip and portal from replacing that origin; closing returns focus there. Healthy preserve-focus guides are suppressed under unrelated modals and do not reopen when the modal closes; their hidden sortable is disabled and their measured chip DOM is released. A failed item keeps its recovery mounted through its own confirmation, while modal presence still suspends application shortcuts. Guide activation and Escape do not reach Canvas session handlers; configured global chords keep normal runtime handling.

Command hints resolve against runtime catalog and mounted extension contributions, including custom bindings, scope conflicts, editable fields and modal exclusions. Command bindings reserved for guide activation or dismissal (bare Enter/Space and Escape chords) are omitted in favor of a usable alternative; fixed Canvas instructions may still describe those keys. Fixed gestures stay Canvas-owned and distinguish selection modifiers at press from constraints during drag. Properties shows them as “On Canvas”; active modal presence hides background guide. Pointer coordinates and pixel epochs are not hint subscriptions.

## Window interactions

- **Geometry is stored once and adapted in CSS.** All windows share one static rule set; stored geometry and stacking rank arrive as inline custom properties (registered as non-inheriting, so a drag restyles window, not widget inside it), so a commit changes values rather than minting a class. Position keeps a 48px sliver reachable (`FLOATING_VIEWPORT_MARGIN_PX`, the same margin `clampWindowToViewport` applies to commits); displayed size is capped to viewport. So a shrinking viewport persists nothing; stored geometry applies again when there is room.
- **Gestures start from the rendered rectangle**, not stored geometry, so a window CSS is clamping or capping does not jump. A gesture commits only what it changed: a move keeps stored size, and a move or resize keeps stored values of any axis it did not change (`commitChangedAxes`), because what is on screen there may only be viewport's clamp or cap. Viewport clamp applies to changed axes alone, so a vertical move or resize never rewrites a stored x, nor a horizontal one a stored y. An axis counts as changed only when the clamp lets the change show: a push against the viewport's edge keeps the stored value too. Gestures clamp against the viewport as CSS resolves `100vw`/`100vh`, measured from a hidden fixed probe in the window, not `innerWidth`/`innerHeight`: at a fractional zoom the viewport is fractional pixels, which those round, and a rounded edge would read a push into the real one as a move. A press that never moves, or a drag against minimum, cap, or edge, commits nothing. Keyboard steps follow the same rules.
- **One commit per gesture.** Pointer moves are coalesced to animation frames and previewed as inline custom properties on window element; store is written once, when gesture ends: on release, or when pointer is taken away (`pointercancel`, a release the page never saw), which keeps what was dragged so far. Escape discards preview. Each keyboard step is its own commit.
- **Resize handles.** Eight pointer-only handles (four edges, four corners) straddle border with matching cursors and non-overlapping hit areas, above an isolated content frame so widget stacking cannot cover them. Inside bottom-right corner sits `ResizeCorner`, the single labelled, keyboard-operable resize control; pointer-only handle there is clipped to band outside border. That control announces size on screen (stored size as viewport caps it) and follows viewport, so its value and keyboard steps agree, to within the sub-pixel difference at a fractional zoom: it announces whole pixels from `innerWidth`/`innerHeight`, while steps cap at the measured viewport. `resizeFloatingGeometry` anchors opposite side, holds size between minimum and viewport (a viewport smaller than minimum lowers it to viewport, so shown size is not mistaken for a resize), and stops top edge at viewport's top.
- **One gesture path.** Title bar, grip, and every handle start through window's single pointer session, so a new gesture replaces the one before it and resize gestures all raise platform's resize-drag signal. Preview names the mode the gesture began in and applies only while window is still in that mode: a window that maximizes or collapses under a gesture shows its new frame at once, and gesture ends itself (releasing drag cursor, committing nothing) next time it hears from pointer. Docking, removing, or switching project unmounts host (hosts keyed by project and instance), which aborts session.
- **Title bar.** Double-click maximizes or restores, and expands a collapsed window; Restore returns to windowed geometry, which maximizing never touches. Collapse and Expand are explicit buttons; Close removes a placed window as a marker's Remove does (an undoable layout step), sending focus to the center when it gets its view back, else to the panel the window's rail shows, else the center; a guest window's Close forgets the guest and sends focus to the center. Label truncates first, down to its icon; contributed widget actions then give way in a strip that scrolls, without a scrollbar, by focus, sideways scroll, or touch, so a focused action is always in view with its ring; window's own controls never shrink.
- **Shaded bodies stay mounted.** Shaded body is hidden with React `Activity`, so its local state survives and no second copy mounts. Drafts are flushed before shading, docking, and removing, because hiding or unmounting an editor stops its flusher.

## Docked bodies

A left, right or bottom panel, and a window, puts its widget's body in one vertical `Scrollable` (`PanelBodySlot` in `WidgetRenderer.tsx`); the manifest's `chrome.body` says how the view meets it.

- **`flow` (default).** The scroll content grows with the view and is never shrunk below it, because the scroll area sizes its thumb from that element: a squeezed one leaves the scrollbar stale as sections open and fold. A view's `h="full"` means at least the body's height, never a bound.
- **`fill`.** For views that bound their own regions: inner lists and trees that scroll themselves, resizable panes, filters or footers that stay in view. The frame wraps the view in a size-contained column, so the view's rows never count toward the body's height and the view gets exactly the body's height. Past the view's own minimum heights the overflow still spills into the body, which then scrolls instead of crushing them. The center host gives every view exactly its height, with no outer scroll, whatever the manifest says.
- **Windows.** A window's body is sized as a docked panel's, by the same rules and with the widget's footer; its title bar is the header. A window shows the surface of the region it returns to (`WidgetViewProps.surface`): the workflow widget renders its form in a window standing for the left rail and its graph otherwise.

## Center chrome

Center view's header floats over its body as two islands (`workbench/shell/CenterArea.tsx`): **Back to {stage}** while Away, view menu and widget label at start, toolbar widgets and header actions at end. Back compacts with the view menu, to its arrow, keeping its accessible name and a tooltip naming it while its label is truncated or hidden; while Away the start island's floor counts that compact width too, so the marker stays on screen however wide the end island grows.

- **Start gives way first.** End island keeps its natural width up to the center width less the start island's floor and a gap; start island takes what remains. The floor (`getChromeIslandMinWidth`) is the view menu's own minimum (5rem: its icon, a few letters, its chevron) plus the island's border, row padding, and end cue, so the menu's minimum stays clear of the cue. Islands never overlap or leave the center.
- **Rows scroll, then cue.** Inside an island, labels truncate to their own minimums first; past that the row scrolls sideways without a scrollbar, by wheel, swipe, or focus (`workbench/shell/ChromeIsland.tsx`). Each end hiding controls shows a fade into the island's background and a chevron button that scrolls to that end, smoothly unless reduced motion is on. The whole cue takes the pointer: the half-hidden controls under the fade neither take clicks nor show hover, and a press on the fade does nothing, not even move focus. A wheel or trackpad swipe over a cue still scrolls the row. The row is its own stacking context, so a control's z-index cannot lift it above the cues. Cues re-measure on scroll, on resizes of the row and its controls, and on any change inside the row, such as a counter gaining a digit. The buttons stay out of the tab order like other pointer shortcuts: focus already scrolls each control into view, clear of the cues.

## Render recovery

The editor store creates transient recovery entries for the active project's instances before publishing its snapshot. Leaving the project or removing an instance drops its entries. The requesting view subscription fences pending reloads through hide, unmount and development remounts; disposal releases its store when pending actions settle. Late callbacks and reload confirmations are fenced by account, project, entry identity, view lifetime and generation. Old-generation failures in unmounted slots are retired after retry; mounted newly failing slots remain isolated. This retirement is not rendering proof for a closed tooltip: a recovered announcement describes currently mounted surfaces, and opening a deterministic failing tooltip can report the failure again.

Boundaries contain failures in their own host and slot (body, label, actions, icon, header, footer or tooltip). They share one retry generation and one implementation load, never another slot's render error. Retry resets failed boundaries without remounting healthy bodies or discarding their local state. Center implementation-load failures expose one expanded recovery action; menu icons keep their static identity. An explicit non-isolation policy still propagates errors.

Compact recovery uses a Platform button named with the widget label, failure and action; only Enter/Space activation is stopped. Its tooltip uses the error message, while expanded recovery and logs retain stacks. A failed compact row suspends its enclosing open action; a tooltip-only failure keeps the healthy row and panels and adds a sibling retry. Status popover triggers retain their DOM shape; closing returns to the usable trigger or the named failed host. Expanded popovers/dialogs and compact status recovery focus a stable named host; docked and floating recovery use the focus controller, including pending-import cancellation. Mounted empty live regions announce failure, retry and committed recovery without entering the compact chip's name.

Retry only reimports through the shared resource and never reloads the document. A repeated rejection offers a separate **Reload editor** action. Its confirmation explains that registered edits are saved first but Canvas undo and per-workflow edit histories are lost for **all open projects**, and a persistent module error may remain. Cancel preserves the histories. Only confirmation runs the Workbench save/pixel barriers before requesting a fresh document. Pending changes, conflicts, failed uploads/saves or newer edits refuse the reload and report an error while the shell stays usable. Ended accounts and removed owners cannot authorize a reload. A confirmation expires across hide/reveal or a later retry generation. Confirming it while the same account, project and instance remain current and its view is visible reports the localized inactive reason without invoking persistence or reload; account/project departure, instance removal and an unmounted or still-hidden view stay silent. No module URL is rewritten. Render failures in an already-loaded implementation retry in place. Shell docking, closing and placement controls remain outside implementation failure slots.
