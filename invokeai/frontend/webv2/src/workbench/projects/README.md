# Project persistence

The backend project record is authoritative. Writes use `expected_revision`; a divergent revision or remotely deleted project requires an explicit user decision. Editing can continue while that decision is pending. Saving a copy reuses one reserved identity through `createProjectSettled`, including after a lost response.

`ProjectDocumentV3` allowlists editable document fields. Optional fields added within schema 3 (`lastFloatingGeometry`, `presetWorkingLayouts`) are additive: absent means none, so older schema-3 documents load unchanged, and a build that predates a field ignores it and drops it from the next document it saves to the server rather than refusing the project, which a schema bump would do. Queue runs, events, undo and per-workflow edit histories are not project documents. Documents are limited to 32 MiB of UTF-8 JSON on both sides of the API.

## Workflows

A project owns an ordered workflow collection (`workflows.entries`) and remembers its active workflow. Each entry carries the editable document, optional source metadata (the library template it was opened from or last explicitly saved to, with the content revision then observed, or `null` when unknown) and the newest successful run's output. Source metadata sits beside the document, outside graph edit history, so undoing an edit never undoes a save. `projectWorkflows.ts` owns membership, selection and the session histories (one per workflow, 40 entries per project across all of them, structurally shared); Workflow owns editing, serialization, library transport and presentation.

Projects autosave their workflows. The library changes only through explicit publication (`features/workflow/data/publication.ts`): saving as a new template or updating the source at exactly the revision the copy last saw; a stale revision is a 409 the user resolves. Every media reference in every workflow, active or not, takes part in reference indexing, cleanup protection, duplication and archive export.

`migrateProjectDocument` is the one migration boundary. Unversioned (schema 1) and schema 2 documents become schema 3 with their single `projectGraph` as the first, active workflow; a `libraryWorkflowId` becomes a source with an unknown revision, never assumed to match the library's current contents. Server loads, recovery drafts, duplication and `.invk` import all pass through it; every write path emits schema 3. Malformed collections (dangling active id, repeated ids, damaged entries) and structurally damaged workflow documents are refused rather than repaired or replaced with blanks; a refused document is reported, left untouched on the server, and its raw content stays available for export. Same-server duplication keeps source references; `.invk` import clears them, because a portable file never names a library write target.

Canvas uploads carrying a project id await that identity’s acknowledged server creation through the mounted persistence service. Uploads waiting on an unacknowledged project share one serialized creation attempt, and a failed attempt answers further uploads for a few seconds before another is made; later uploads use the acknowledged identity without flushing unrelated edits. Only a closed project, an account change, engine disposal or the operation's own cancellation stops an upload, and those stop the wait immediately. Any other outcome (creation failed or offline, a conflict, or a server that no longer knows the project and refuses the id) sends the upload without a project id. Such uploads are never re-associated with the project later, so the project's intermediates cleanup does not see them.

Project links are consumed after a successful open, so reloading restores the saved active project rather than replaying an earlier link. A new-project startup selects the newly created draft before saving the session.

## Browser recovery

- Account-owned IndexedDB stores only unacknowledged project drafts, unload journal entries, active queue runs, receipt acknowledgements, and bounded recall values. Clean server documents are not mirrored. The journal has a database of its own, deleted with the workbench database by account cleanup and by clearing workspace data.
- Draft generations fence acknowledgements. Draft writer ownership and cross-tab notifications prevent one editor from overwriting another editor's unacknowledged work.
- **Unload journal.** Staging a draft takes fenced read-then-write transactions, which an unloading page never finishes. So when the page is hidden or unloads, before the save starts, each open project whose document is not what the next load would restore (its durably staged draft, or without one the acknowledged server copy) is written as one blind, explicitly committed IndexedDB write. It lives in its own database because Chromium drops such a write at unload while a read-write transaction of the same database is still open, which a stage in flight is. An entry carries the account, project, lineage (an editor session, possibly another tab's that the session blob handed on), the editor session of the page that wrote it, writer, base revision and canvas schema floor, and a draft generation: above everything the writer staged or journaled before, or equal to a stage of the same document still in flight. A writer's generations never restart while its page lives, even when a project is closed and reopened. Each write also deletes the writer's lower generations for the lineage, so there is at most one entry per lineage and writer, however long saves cannot be acknowledged.
- **Settled mark.** A lineage's writer claim records the generation through which its writer has settled its journal: everything it acknowledged, discarded, or holds in recovery. The acknowledgement and the draft deletion write it in the same transaction that settles or deletes the draft; a document back to what recovery holds (an undo, say) writes it on its next save, and claims the lineage for the writer if it has none. It is an optional claim field, so claims written earlier read as having settled nothing and the workbench database stays at version 4; a mark of an earlier writer is ignored. It is what tells "never staged" from "acknowledged and moved on" once an acknowledgement has deleted the draft, so an entry whose deletion failed, or that another tab reconciles at the moment of the acknowledgement, can never come back.
- The next load of the account reconciles every entry, in pages, before any writer claims a lineage. An entry becomes its lineage's next draft only where its writer could still have staged it: the lineage is unclaimed or still claimed by that writer, the writer has not settled that far, and the lineage holds no generation at or above the entry's. It keeps the stored draft's conflict, schema refusal, copy reservation, and base revision, as staging does, and then goes through the usual load rules, so a server revision the base no longer matches surfaces as a conflict. One exception: when the entry replaced a staged draft whose document the server now holds exactly (its save arrived but its answer did not), the draft is rebased onto that revision, as the late answer would have done, instead of conflicting with the writer's own save. An entry is discarded when another writer adopted, reclaimed, or retargeted the lineage, when its writer settled it, when the lineage already holds it or something newer, when it belongs to another account, or when its record schema is unknown or it is damaged. The draft is written before the entry is removed, so a crash in between leaves an entry the next pass discards as superseded.
- Another tab's load reconciles only the entries of pages that are gone. A page proves it is still running by its editor session's Web Lock, which it holds until its last editor releases it or the page unloads or crashes; an entry whose writing page (the editor session it names, not the lineage it is written under) another page still holds is left in place (a merely hidden tab is still writing its lineages, and staging its entry elsewhere would hand that tab's unsaved edit to another tab, where an undo could never retire it). An entry written before it named its page is treated as a gone page's. The hidden page settles the entry with its own saves, or the next load after it is gone recovers it. A browser that keeps a page holding its session in the back/forward cache keeps the lock held, so the entry waits until the page is restored (and saves) or evicted; one that evicts such pages (Chromium today) releases the lock, and the entry is recovered as a gone page's. A reload of the same tab reclaims its session, retrying for up to half a second (five retries 100 ms apart) while the old document lets go, and then reconciles its own entries. Two cases fall outside it. If the old document holds the lock longer, the reload takes a fresh session, its own entries and staged drafts count as a running page's on that load, and a later load recovers them once the old document is gone. A duplicated tab waits the same half second before taking a session of its own; if the original reloads within it, the duplicate can take the original's session instead and then takes the original's entries and staged drafts, while the reloaded original takes a fresh session. Staged drafts follow the same rule: a load does not adopt, auto-open, or offer for recovery a draft whose lineage is named after another running page's session, and the editor route does not count it. A draft records its lineage, not the page staging it, so it is judged by the session that lineage is named after: a lineage isolated for an unopenable draft names no page and is adopted as before. A lineage the session blob hands on (today only isolated ones) is not judged at all: a loading page claims its handed-on lineage directly, whether or not the page staging it still runs. Without Web Locks (a plain-HTTP deployment, say) liveness cannot be told, so every entry is reconciled and every draft is adopted as before. A hidden event during save-as-new journals the source project: if the page goes away before the copy exists, the edit is recovered into the conflicted source and the retried copy keeps its reserved document; once the copy exists, the source lineage has moved, so the entry is discarded and the copy is never written from it.
- An entry the draft store cannot take waits. One for a damaged lineage waits for that lineage's cleanup, for at most 7 days, and is then discarded. One refused for lack of storage is applied by a later load only while its lineage is unclaimed; the load that refused it usually claims the lineage when it opens the project, and then the edit is lost. Both report degraded local recovery for that project until its next stage succeeds. An unavailable journal (its database will not open, or reconciliation fails) is logged, not reported: recovery then works exactly as it did without the journal. A journal operation that fails on its own (a deletion whose transaction could not be opened, say) fails alone; the next hidden event journals again.
- A writer settles and removes its entries when the server acknowledges a generation at or above them, when the document returns to what recovery holds (on the next save; a hidden event meanwhile also deletes the entry, and the save still writes the mark), and when it deletes the project or discards its draft; a removal that fails leaves the entry settled, and one whose mark fails is retried with the next save. When an older generation is acknowledged, a newer entry is rewritten onto the acknowledged revision, as a newer staged draft is rebased. A journal write that aborts is written again on the next hidden event. Nothing is journaled for a closed session, after the account lifetime ended, for a project being deleted, or beyond 8 MiB of documents per event; larger projects rely on autosave, and the skip is logged. The editor route counts projects with entries as ones that would open, so a new project typed into and reloaded before its first save reopens.
- Queue ownership uses Web Locks. Journal writes precede submission; backend receipts make retries safe after lost responses. Accepted IDs must be durable before their receipt can expire. Fresh runs that never reached browser storage use best-effort terminal acknowledgement instead.
- Completed, failed, and cancelled runs retain exact recall values in an LRU cache, capped at 500 entries / 32 MiB. Eviction removes recall convenience, not project data or active-run recovery.
- Projects with journal entries remain reachable even if another tab saved an empty session. Automatic reopening is bounded; remaining entries can be opened, exported as queue-recovery JSON, or explicitly discarded. Discarding local recovery does not cancel backend work.
- Browser-storage failures do not block backend project loads or saves. Recovery warnings distinguish degraded local durability from successful server persistence.

## Leaving the editor

Navigation is never blocked; local capture of committed state is the contract, within the limits below.

- **Exit checkpoint.** When the editor unmounts while its account is current, the persistence runtime stops observing the aggregate and commits drafts editors still hold (the draft registry). It then requests a save of the committed state at once, which queues behind any save in flight, and meanwhile flushes live Canvas pixels for at most 3 seconds. If that flush (or anything else) moved the state on, it saves once more; otherwise there is exactly one write. Each save stages the local recovery draft before pushing to the backend. The runtime and its persistence lease outlive the unmount until the checkpoint settles; if the page is hidden or unloads meanwhile (leaving the editor and reloading at once), it writes the unload journal for the committed state, unless a newer editor has superseded it. A failed or unacknowledged save, and a pixel flush that failed or timed out, are logged; recovery is left exactly as after a failed autosave.
- **Closing the last tab.** The empty session is marked closed when it is requested. From then until the editor leaves, nothing saves, so the project cannot be written back into the session. If the close does not complete (queue work started, the project changed, or the session write failed), the session is reopened and written again, and a save that came due while it was closed (an edit committed meanwhile) runs at once, so its outcome reaches the autosave status and retries as usual.
- **Account changes.** An ended account lifetime abandons its checkpoint: nothing of the old account is written afterwards.
- **Re-entry.** A remounted editor of the same account loads only after the previous checkpoint has settled and its persistence has closed, so it never hydrates an older snapshot and two editors never write at once. The provider keeps that handoff per account lifetime, keyed by its scope, so another account never waits on it.
- **Re-entry after 10 seconds.** The new editor loads anyway. The previous checkpoint is superseded: it starts no further write and gives up its project mutation locks. If it still had an unsaved revision, it logs that the revision was not written. Staging happens inside the persistence queue, so while a request stalls nothing newer than the save before it reaches local recovery; edits committed after that are lost in this case, and also if the tab is closed during the wait. The stalled request is not cancelled. Until it returns, or the tab closes, the superseded persistence keeps its draft-store connection and its hold on the tab's editor session. The new editor holds the same session, which stays locked to this tab until its last holder releases it. A late write is fenced like another tab's, by draft-writer claims and revision conflicts.
- **Hidden pages.** On `pagehide` and when the page becomes hidden, the runtime commits drafts editors still hold (the draft registry), writes the unload journal for an unsaved revision (including one whose save is in flight), then saves it at once instead of after the autosave debounce. Committing a draft leaves the control's value, caret and focus as they were. A revision whose save failed, or one already being saved, is not sent again; while the session is closed nothing is committed, journaled, or saved. The save is asynchronous, so it completes when the hidden page keeps running (switching tabs or apps, minimising, or entering the back/forward cache), and its acknowledgement retires the journal. It cannot complete while the page unloads (reload, closing the tab, navigating away), so across an unload the journal is what survives: the next load of the account recovers the edit as a pending draft and saves it. A tab restored from the back/forward cache writes through the same account-scope, draft-writer, and revision checks as every other write. There is no unload prompt.
- **What is and is not guaranteed.** In Chromium, an ordinary reload, tab close, or navigation away right after an edit keeps the edit, including one still held in a debounced field: the journal write is committed before the handler returns and the browser finishes it. Nothing is guaranteed when the browser or operating system is killed, crashes, or loses power before the write reaches disk (the transaction uses the default, relaxed durability), when a page is discarded without a `pagehide` or hidden event (an edit made after the last hidden event is lost), for projects over the journal budget, or when browser storage is unavailable or full. An undo made just before the page goes away is retired by the same kind of blind write and can be lost the same way: then the undone edit comes back on the next load, silently when the server revision has not moved. Other browsers follow the same IndexedDB rules but have not been verified to finish a committed write during unload.
- **Journal side effects.** An entry kept for a damaged lineage or for full storage reports degraded local recovery for its project on every load that keeps it, even when that project is not opened in the session. The editor route counts any project with an entry of a page that is gone (or of this page, by the session it persisted) as one that would open, so with an empty session such an entry, or one that reconciliation will discard, opens the editor instead of Home; an entry or staged draft of another page that still runs does not, since the editor would leave it alone.
- **Project transitions.** Creating, opening, switching, and closing projects commit pending editor drafts at the moment the open or active projects change, so an edit typed while a caller awaited hydration or a close push lands on the project it was typed in. Close can require the version it pushed; drafts that change the project refuse it, and the close flow pushes again.

## Intentional cutover

The old workbench mirror, sync map, and refused-project localStorage keys are deleted on initialization. Their contents are not migrated. Export any needed browser-only work with the old build before upgrading.

Cold-start offline editing is not supported. When the backend cannot load, the unavailable screen provides retry and local draft/run exports. Conflicted or schema-refused drafts are retained until explicitly resolved or deleted; they are never silently evicted.

## Additive canvas values

A new value in a closed canvas set, such as a control layer's adapter kind (`anima_lllite`), is added without raising the canvas schema version or the project's compatibility floor. Builds that know the value load and save it unchanged; builds that do not refuse the canvas rather than rewrite it, because coercing an unknown kind to a known one would replace the user's adapter on the next autosave. In an older build the project is not opened and the user sees that it "contains canvas data this version of Invoke cannot read"; the saved copy is untouched and can be exported, and a build that knows the value opens it as saved. Raise the schema version instead when older builds could misread a document without refusing it.

Load does not reinterpret a known value either. An Anima control layer saved as ControlNet before ControlNet-LLLite was supported keeps its kind and model; the layer settings name the adapter type to switch to and offer a one-step switch that keeps the model, weight and step range where the new kind can use them.

## Font dependencies

Custom text retains an immutable font reference and explicit variation coordinates. Browser registration names are runtime state and never enter the project document. New typography requires Canvas schema 4; documents without it retain their existing compatibility floor.

Project archives record font dependencies by content hash. Export defaults to references only; **Include font files** embeds the original referenced files, once per hash, after authenticated download and checksum verification. A failed required font download fails the embedded export rather than producing a silently incomplete archive.

Import verifies declared entries and checksums, then validates all embedded fonts before creating server resources. Fonts are uploaded privately and the canonical document's references are remapped to the destination IDs. Duplicate uploads reuse existing private records. Rollback removes only newly created fonts and only when project creation has not been attempted or has confirmed absence; an ambiguous create response retains the resources. Font quota failures offer an explicit references-only retry. Changing accounts cancels the operation and prevents cleanup under another user's credentials.
