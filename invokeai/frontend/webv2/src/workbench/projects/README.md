# Project persistence

Paths are relative to the webv2 `src/` directory.

Backend project record is authoritative. Writes use `expected_revision`; divergent revision or remotely deleted project needs explicit user decision. Editing can continue while that decision pends. Saving a copy reuses one reserved identity through `createProjectSettled`, including after a lost response.

`ProjectDocumentV3` allowlists editable document fields. Optional fields added within schema 3 (`lastFloatingGeometry`, `presetWorkingLayouts`) are additive: absent means none, so older schema-3 documents load unchanged, and a build predating a field ignores it and drops it from the next document it saves to the server instead of refusing the project (a schema bump would refuse it). Queue runs, events, undo and per-workflow edit histories are not project documents. Documents capped at 32 MiB of UTF-8 JSON on both sides of the API.

## Content and workspace

The server holds a project as two documents (document schema 4): its **content**, what the project is and every member shares (name; the canvas document, its snapshots and revision counter; workflow entries), and each member's **workspace**, how they work on it (layout, widgets and generation settings, prompt history, project settings, the canvas selection and staging area, the open workflow and each workflow's last run). The browser keeps one whole document per project, in memory, drafts and the unload journal; `workbench/projects/projectHalves.ts` splits it at the server boundary and joins the two halves back when a project loads. A member with no workspace yet joins onto the workspace a new project starts with.

Each half has its own revision. A project the server holds whole (saved before the split) is split by its next save, whether or not anything changed, unless it is conflicted or refused: one `PUT /projects/{id}` carries the content, the document floor of 4 (so a build that predates the split is refused the project rather than saving it whole) and the member's workspace, which the server stores with the content in one transaction and answers beside it. The split of a whole project never lands without the member's workspace (the server refuses it without one), so a page gone right after that request (sign-out deletes its drafts) loses nothing; a workspace revision mismatch refuses the content with it. Every create is one request the same way: a project's first save, a save as a copy, an import and a duplicate send the content with the creator's workspace (`POST /projects` with `workspace`), and the answer carries the workspace it stored, so the server never holds a split project's content without its creator's workspace. A document created whole (below) carries the workspace inside and sends none; the server refuses a workspace beside a whole document. A create settled by a read of an earlier attempt that committed unanswered is judged by its content, so the workspace it answers with is taken as pushed only when it is the one this save sent; otherwise it stays owed and is saved next against the revision the answer named. Which board a created workspace names follows two conventions, both right because load applies `applyAuthoritativeProjectBoard(..., { selectBoard: false })`: import and duplicate stage the inbox first, so the workspace in the create already names it; a project's first save sends the workspace without a board, and `pendingBoardAssignments` applies the one the answer minted locally, which the next save writes. Only once split are the halves saved separately, and a save then sends only the half that changed: the content first, then the workspace, one after the other, since the server takes one project write per account at a time; every project write declares the canvas and document schemas the build reads, and the server refuses one above them. Each half is recorded as acknowledged as soon as it is, so a retry sends only what is still owed, and a content acknowledgement rebases the lineage's draft and journal entry before the workspace is sent, so recovery after a failed workspace save builds on the saved content. The draft is acknowledged when both are. A revision conflict in either half follows the same "changed elsewhere" flow, and the banner says when it is the caller's settings; using the server version then takes the server's workspace and keeps this tab's latest content, unless the server's content has moved since this tab's base, which is then reported as a content conflict instead. On a revision conflict a half the server holds as one of the page's own recent sends (its answer lost) is retried, not reported, which covers the split whose answer was lost. A project whose workflow repeats an item id (possible only before the split) keeps saving whole instead, and its first save, a save as a copy, or a duplicate of it creates it whole, since split content repeating one would be refused by every later load. A split project whose workflow comes to repeat one (only an editing bug could) is not saved, and the error asks for the change to be undone; export would flush the same save, so it cannot be the way out.

Drafts and journal entries carry a base revision for each half (`baseRevision` for the content, `baseWorkspaceRevision`, absent in records written before the split, for the workspace). A recovered draft is judged half by half: a half equal to the server's needs no base, which covers a page that saved the content and was gone before the workspace, and a changed half conflicts only when the server moved it past the draft's base.

## Workflows

Project owns an ordered workflow collection (`workflows.entries`) and remembers its active workflow. Each entry carries the editable document, optional source metadata (library template it was opened from or last explicitly saved to, with the content revision then observed, or `null` when unknown) and the newest successful run's output. Source metadata sits beside the document, outside graph edit history, so undoing an edit never undoes a save. `workbench/projectWorkflows.ts` owns membership, selection and session histories (one per workflow, 40 entries per project across all, structurally shared); Workflow owns editing, serialization, library transport, presentation.

Projects autosave their workflows. Library changes only through explicit publication (`features/workflow/data/publication.ts`): save as new template, or update the source at exactly the revision the copy last saw; stale revision is a 409 the user resolves. Every media reference in every workflow, active or not, joins reference indexing, cleanup protection, duplication and archive export.

`migrateProjectDocument` is the one migration boundary. Unversioned (schema 1) and schema 2 documents become schema 3 with their single `projectGraph` as first, active workflow; a `libraryWorkflowId` becomes a source with unknown revision, never assumed to match the library's current contents. Server loads (after joining a split project's halves), recovery drafts, duplication and `.invk` import all pass through it; every local document is schema 3. Every sync-engine save is the split of one, except a project whose workflow repeats an item id (above); renaming a closed project the server holds whole still writes a whole document, which the project's next save from an editor splits. `.invk` import (format v3: `project.json` content beside optional `workspace.json`, which becomes the importer's workspace) and duplication create the content and the creator's workspace in one request, the workspace already open on the inbox board the create claims: an inbox is always staged first (an empty one for a file without boards), so its id is known before the create and nothing is written after it but the other boards' placement. Malformed collections (dangling active id, repeated ids, damaged entries) and structurally damaged workflow documents are refused, not repaired or replaced with blanks; refused document is reported, left untouched on the server, raw content stays exportable. Same-server duplication keeps source references; `.invk` import clears them, since a portable file never names a library write target.

Canvas uploads carrying a project id await that identity’s acknowledged server creation through the mounted persistence service. Uploads waiting on an unacknowledged project share one serialized creation attempt; a failed attempt answers further uploads for a few seconds before another is made; later uploads use the acknowledged identity without flushing unrelated edits. Only a closed project, account change, engine disposal or the operation's own cancellation stops an upload, and those stop the wait immediately. Any other outcome (creation failed or offline, conflict, or server that no longer knows the project and refuses the id) sends the upload without project id. Such uploads are never re-associated with the project later, so project's intermediates cleanup does not see them.

Project links are consumed after successful open, so reload restores the saved active project, not an earlier link. New-project startup selects the newly created draft before saving the session.

Workflow reads the active workflow through the App-composed port and edits, publishes, presents documents; it never replaces authored project work. Library is written only by the Workflow-owned publication controller, which captures account, project, workflow and content before start, refuses to overlap itself per workflow, reconciles a lost answer against the destination record before resending, and records resulting library id and revision on the originating workflow alone. Queue submissions carry the originating project workflow so seed advances, node progress and run previews return to it whatever is active later.

## Persistence runtime

Workbench persistence is scoped to one mounted Workbench and its account lifetime. `createWorkbenchPersistenceRuntime` owns hydration ordering, debounced autosave, hidden-page saves, revision/generation checks, conflict application, reconnect replay, status publication, exit checkpoint, without importing React. `createSyncedWorkbenchPersistence` builds local/remote project sync state for one mounted Workbench; no process-wide maps, sets, flags, or caches hold that state. It also owns the unload journal: runtime asks it, via its persistence port, to journal unsaved state synchronously when page is hidden or unloads, and its load reconciles the journal into the draft store under the draft store's fencing rules. `WorkbenchProvider` constructs these lifetimes, starts the runtime and ends it with its exit checkpoint through the mount lifecycle adapter, and selects aggregate hydration state. Checkpoint and persistence lease outlive the unmount until it settles. Provider also hands the checkpoint to the account lifetime's next editor through a module-level map keyed by account scope; that editor loads after it, waiting at most 10 seconds; the tab's editor session is reference-counted across the two. Project transition commands commit pending editor drafts themselves, so callers do not flush before creating, opening, switching, or closing a project.

## Browser recovery

- Account-owned IndexedDB stores only unacknowledged project drafts, unload journal entries, active queue runs, receipt acknowledgements, bounded recall values. Clean server documents not mirrored. Journal has its own database, deleted with the workbench database by account cleanup and by clearing workspace data.
- Draft generations fence acknowledgements. Draft writer ownership and cross-tab notifications stop one editor overwriting another editor's unacknowledged work.
- **Unload journal.** Staging a draft takes fenced read-then-write transactions, which an unloading page never finishes. So when page is hidden or unloads, before save starts, each open project whose document is not what next load would restore (its durably staged draft, or without one the acknowledged server copy) is written as one blind, explicitly committed IndexedDB write. Own database because Chromium drops such a write at unload while a read-write transaction of the same database is still open, which a stage in flight is. Entry carries account, project, lineage (an editor session, possibly another tab's that the session blob handed on), editor session of the page that wrote it, writer, base revisions and canvas schema floor, and a draft generation: above everything the writer staged or journaled before, or equal to a still-in-flight stage of the same document. A writer's generations never restart while its page lives, even when a project is closed and reopened. Each write also deletes the writer's lower generations for the lineage, so at most one entry per lineage and writer, however long saves cannot be acknowledged.
- **Settled mark.** A lineage's writer claim records the generation through which its writer settled its journal: everything it acknowledged, discarded, or holds in recovery. Acknowledgement and draft deletion write it in the same transaction that settles or deletes the draft; a document back to what recovery holds (an undo, say) writes it on its next save, and claims the lineage for the writer if it has none. Optional claim field, so earlier claims read as settled nothing and workbench database stays at version 4; an earlier writer's mark is ignored. It tells "never staged" from "acknowledged and moved on" once an acknowledgement deleted the draft, so an entry whose deletion failed, or that another tab reconciles at the moment of acknowledgement, can never come back.
- Next load of the account reconciles every entry, in pages, before any writer claims a lineage. Entry becomes its lineage's next draft only where its writer could still have staged it: lineage unclaimed or still claimed by that writer, writer has not settled that far, and lineage holds no generation at or above the entry's. It keeps the stored draft's conflict, schema refusal, copy reservation, and base revision, as staging does, then goes through usual load rules, so a server revision the base no longer matches surfaces as conflict. One exception: when the entry replaced a staged draft whose document the server now holds exactly (its save arrived, its answer did not), the draft is rebased onto that revision, as the late answer would have done, instead of conflicting with the writer's own save. Entry discarded when another writer adopted, reclaimed, or retargeted the lineage, when its writer settled it, when lineage already holds it or something newer, when it belongs to another account, or when its record schema is unknown or it is damaged. Draft written before entry removed, so a crash between leaves an entry the next pass discards as superseded.
- Another tab's load reconciles only entries of pages that are gone. Page proves it still runs by its editor session's Web Lock, held until its last editor releases it or the page unloads or crashes; an entry whose writing page (the editor session it names, not the lineage it is written under) another page still holds is left in place (a merely hidden tab still writes its lineages, and staging its entry elsewhere would hand that tab's unsaved edit to another tab, where an undo could never retire it). Entry written before it named its page counts as a gone page's. Hidden page settles the entry with its own saves, or next load after it is gone recovers it. Browser that keeps a page holding its session in the back/forward cache keeps the lock held, so the entry waits until the page is restored (and saves) or evicted; one that evicts such pages (Chromium today) releases the lock, and the entry is recovered as a gone page's. Reload of same tab reclaims its session, retrying up to half a second (five retries 100 ms apart) while old document lets go, then reconciles its own entries. Two cases fall outside it. If old document holds the lock longer, reload takes a fresh session, its own entries and staged drafts count as a running page's on that load, and a later load recovers them once old document is gone. Duplicated tab waits the same half second before taking its own session; if the original reloads within it, the duplicate can take the original's session instead and then takes the original's entries and staged drafts, while reloaded original takes a fresh session. Staged drafts follow same rule: a load does not adopt, auto-open, or offer for recovery a draft whose lineage is named after another running page's session, and editor route does not count it. Draft records its lineage, not the page staging it, so it is judged by the session that lineage is named after: a lineage isolated for an unopenable draft names no page and is adopted as before. A lineage the session blob hands on (today only isolated ones) is not judged at all: loading page claims its handed-on lineage directly, whether or not the page staging it still runs. Without Web Locks (plain-HTTP deployment, say) liveness cannot be told, so every entry is reconciled and every draft adopted as before. Hidden event during save-as-new journals the source project: if page goes away before the copy exists, edit is recovered into the conflicted source and retried copy keeps its reserved document; once copy exists, source lineage has moved, so entry is discarded and copy is never written from it.
- Entry the draft store cannot take waits. One for a damaged lineage waits for that lineage's cleanup, at most 7 days, then is discarded. One refused for lack of storage is applied by a later load only while its lineage is unclaimed; the load that refused it usually claims the lineage when it opens the project, and then the edit is lost. Both report degraded local recovery for that project until its next stage succeeds. Unavailable journal (database will not open, or reconciliation fails) is logged, not reported: recovery then works exactly as without the journal. A journal operation failing on its own (a deletion whose transaction could not open, say) fails alone; next hidden event journals again.
- Writer settles and removes its entries when server acknowledges a generation at or above them, when document returns to what recovery holds (on next save; a hidden event meanwhile also deletes the entry, and the save still writes the mark), and when it deletes the project or discards its draft; failed removal leaves the entry settled, and one whose mark fails is retried with the next save. When an older generation is acknowledged, a newer entry is rewritten onto the acknowledged revision, as a newer staged draft is rebased. Aborted journal write is written again on next hidden event. Nothing journaled for a closed session, after account lifetime ended, for a project being deleted, or beyond 8 MiB of documents per event; larger projects rely on autosave, and the skip is logged. Editor route counts projects with entries as ones that would open, so a new project typed into and reloaded before its first save reopens.
- Queue ownership uses Web Locks. Journal writes precede submission; backend receipts make retries safe after lost responses. Accepted IDs must be durable before their receipt can expire. Fresh runs that never reached browser storage use best-effort terminal acknowledgement instead.
- Completed, failed, and cancelled runs keep exact recall values in an LRU cache, capped at 500 entries / 32 MiB. Eviction removes recall convenience, not project data or active-run recovery.
- Projects with journal entries stay reachable even if another tab saved an empty session. Automatic reopening is bounded; remaining entries can be opened, exported as queue-recovery JSON, or explicitly discarded. Discarding local recovery does not cancel backend work.
- Browser-storage failures do not block backend project loads or saves. Recovery warnings separate degraded local durability from successful server persistence.

## Leaving the editor

Navigation never blocked; local capture of committed state is the contract, within limits below.

- **Exit checkpoint.** When editor unmounts while its account is current, persistence runtime stops observing the aggregate and commits drafts editors still hold (the draft registry). Then requests a save of committed state at once, queued behind any save in flight, and meanwhile flushes live Canvas pixels for at most 3 seconds. If that flush (or anything else) moved the state on, it saves once more; otherwise exactly one write. Each save stages the local recovery draft before pushing to backend. Runtime and its persistence lease outlive the unmount until checkpoint settles; if page is hidden or unloads meanwhile (leaving editor and reloading at once), it writes the unload journal for committed state, unless a newer editor superseded it. Failed or unacknowledged save, and pixel flush that failed or timed out, are logged; recovery left exactly as after a failed autosave.
- **Closing the last tab.** Empty session is marked closed when requested. From then until editor leaves, nothing saves, so project cannot be written back into the session. If close does not complete (queue work started, project changed, or session write failed), session is reopened and written again, and a save that came due while closed (an edit committed meanwhile) runs at once, so its outcome reaches autosave status and retries as usual.
- **Account changes.** Ended account lifetime abandons its checkpoint: nothing of the old account is written afterwards.
- **Re-entry.** Remounted editor of same account loads only after previous checkpoint settled and its persistence closed, so it never hydrates an older snapshot and two editors never write at once. Provider keeps that handoff per account lifetime, keyed by its scope, so another account never waits on it.
- **Re-entry after 10 seconds.** New editor loads anyway. Previous checkpoint is superseded: starts no further write and gives up its project mutation locks. If it still had an unsaved revision, it logs that the revision was not written. Staging happens inside the persistence queue, so while a request stalls nothing newer than the save before it reaches local recovery; edits committed after that are lost in this case, and also if tab is closed during the wait. Stalled request is not cancelled. Until it returns, or tab closes, superseded persistence keeps its draft-store connection and its hold on the tab's editor session. New editor holds the same session, which stays locked to this tab until its last holder releases it. Late write is fenced like another tab's, by draft-writer claims and revision conflicts.
- **Hidden pages.** On `pagehide` and when page becomes hidden, runtime commits drafts editors still hold (the draft registry), writes the unload journal for an unsaved revision (including one whose save is in flight), then saves it at once instead of after autosave debounce. Committing a draft leaves control's value, caret and focus as they were. Revision whose save failed, or one already being saved, is not sent again; while session is closed nothing is committed, journaled, or saved. Save is asynchronous, so it completes when the hidden page keeps running (switching tabs or apps, minimising, or entering back/forward cache), and its acknowledgement retires the journal. It cannot complete while page unloads (reload, closing tab, navigating away), so across an unload the journal is what survives: next load of the account recovers the edit as a pending draft and saves it. Tab restored from back/forward cache writes through the same account-scope, draft-writer, and revision checks as every other write. No unload prompt.
- **What is and is not guaranteed.** In Chromium, an ordinary reload, tab close, or navigation away right after an edit keeps the edit, including one still held in a debounced field: journal write is committed before the handler returns and the browser finishes it. Nothing guaranteed when browser or OS is killed, crashes, or loses power before the write reaches disk (transaction uses default, relaxed durability), when a page is discarded without a `pagehide` or hidden event (edit made after last hidden event is lost), for projects over the journal budget, or when browser storage is unavailable or full. Undo made just before page goes away is retired by the same kind of blind write and can be lost the same way: then the undone edit comes back on next load, silently when server revision has not moved. Other browsers follow same IndexedDB rules but are not verified to finish a committed write during unload.
- **Journal side effects.** Entry kept for a damaged lineage or full storage reports degraded local recovery for its project on every load that keeps it, even when that project is not opened in the session. Editor route counts any project with an entry of a gone page (or of this page, by the session it persisted) as one that would open, so with an empty session such an entry, or one reconciliation will discard, opens the editor instead of Home; an entry or staged draft of another still-running page does not, since editor would leave it alone.
- **Project transitions.** Creating, opening, switching, and closing projects commit pending editor drafts the moment open or active projects change, so an edit typed while a caller awaited hydration or a close push lands on the project it was typed in. Close can require the version it pushed; drafts that change the project refuse it, and close flow pushes again.

## Intentional cutover

Old workbench mirror, sync map, and refused-project localStorage keys are deleted on initialization. Contents not migrated. Export any needed browser-only work with the old build before upgrading.

Cold-start offline editing not supported. When backend cannot load, unavailable screen offers retry and local draft/run exports. Conflicted or schema-refused drafts kept until explicitly resolved or deleted; never silently evicted.

## Additive canvas values

New value in a closed canvas set, such as a control layer's adapter kind (`anima_lllite`), is added without raising canvas schema version or project's compatibility floor. Builds that know the value load and save it unchanged; builds that do not refuse the canvas instead of rewriting it, since coercing an unknown kind to a known one would replace the user's adapter on next autosave. In an older build the project is not opened and user sees that it "contains canvas data this version of Invoke cannot read"; saved copy is untouched and exportable, and a build that knows the value opens it as saved. Raise schema version instead when older builds could misread a document without refusing it.

Load does not reinterpret a known value either. Anima control layer saved as ControlNet before ControlNet-LLLite was supported keeps its kind and model; layer settings name the adapter type to switch to and offer a one-step switch that keeps model, weight and step range where the new kind can use them.

## Font dependencies

Custom text keeps an immutable font reference and explicit variation coordinates. Browser registration names are runtime state, never enter the project document. New typography requires Canvas schema 4; documents without it keep their existing compatibility floor.

Project archives record font dependencies by content hash. Export defaults to references only; **Include font files** embeds original referenced files, once per hash, after authenticated download and checksum verification. Failed required font download fails the embedded export instead of producing a silently incomplete archive.

Import verifies declared entries and checksums, then validates all embedded fonts before creating server resources. Fonts uploaded privately; canonical document's references remapped to destination IDs. Duplicate uploads reuse existing private records. Rollback removes only newly created fonts and only when project creation was not attempted or has confirmed absence; ambiguous create response keeps the resources. Font quota failures offer explicit references-only retry. Changing accounts cancels the operation and prevents cleanup under another user's credentials.

## Verification

Run `pnpm lint`, `pnpm test`, `pnpm test:browser`, and `pnpm run test:performance:build` from webv2. Queue receipt tests also cover backend admission, account isolation, project deletion, partial acceptance, idempotent retries. Browser tests exercise real IndexedDB transactions and Web Locks.
