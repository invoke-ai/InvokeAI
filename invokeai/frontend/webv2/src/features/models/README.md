# Models catalog

Paths are relative to the webv2 `src/` directory.

`features/models/data/modelsStore.ts` owns the shared catalog snapshot and by-key index. List refreshes are single-flight with at most one queued trailing read. Local model replacement, narrow patches (including optimistic rollback), deletion, and cover changes advance a mutation generation. A read started before that generation cannot replace the catalog or publish an obsolete error; it queues an authoritative trailing read so unrelated server changes remain visible. Cover URL versions remain local cache-busting state. Only successful mutation callers apply confirmed changes; a failed request alone does not supersede a valid read.

The catalog keeps the server's order, because features read `models` and take the first match. Install order is a separate read of the same listing (`order_by=created_at`) into `dateAddedRanks`, a key-to-rank map. It starts once the library's Date added sort asks for it (`ensureDateAddedOrderLoaded`) and then runs inside each refresh, so the ranks and the catalog come from the same refresh; a failed order read keeps the previous ranks and is reported to whoever asked. A model the ranks do not list sorts as the newest, and until the ranks load that sort lists by name.

Account reset clears the catalog and flight state. Responses from an earlier account lifetime cannot update the current catalog or schedule reads for it.

## Architecture table

`features/models/core/architectureCapabilities.ts` holds the backend's architecture table (`GET /api/v2/models/capabilities`), pinned to the backend by `core/__fixtures__/architectureCapabilities.json` and `tests/backend/architectures/test_capabilities_fixture.py`. It rejects a malformed table without publishing it. `data/architectureCapabilitiesStore.ts` loads it on demand (`ensureArchitectureCapabilitiesLoaded`): single-flight, retried after a failure, cleared with the account and reloaded for the next one if anything had asked for it. Pure cores read it through the `architectures` entry, which may reach only Models' `core/` (`PURE_FEATURE_ENTRIES` in `architecture/featureInterfaces.ts`), and loaders through `architecturesStore`. Neither is on the `index` barrel, so the Launchpad's startup graph never requests the table.

`architectureAcceptsVae` is the VAE pairing rule, the backend's `accepts_vae`: with no row nothing is accepted, a row without a `vae` block accepts its own base, and listed latent widths must match. Generation's VAE picker, validator and compiler ask it with the main's variant, and so do Related Models' links to a main. Any other host (a LoRA, a ControlNet) names no main variant, so its links follow `someArchitectureVariantAcceptsVae`, the backend's variant-agnostic `accepted_vae_bases`: a VAE that some row of the base accepts, at that row's latent width. The `architectures` entry exposes reads and `withArchitectureCapabilities` (a table held for one offline run, such as graph export); only the store publishes tables. Generation maps rows onto its own policy (`generation/core/architectureGenerationConfig.ts`).

Related Models decides VAE links only from the loaded table. Its add-link picker requests the table when it opens; while the table loads or after it failed, the picker lists the links it can decide and says why VAE links are missing, with a retry after a failure. Links that are not VAE pairs never wait for the table.
