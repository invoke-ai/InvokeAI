# Workflow library browsing

Paths are relative to the webv2 package.

`src/features/workflow/data/libraryBrowseStore.ts` owns account-scoped server listings, navigation positions, and demand-driven enrichment. Search, category/visibility, tags, order, totals and tag counts are server-authoritative. A result position is a server offset, not an index in a locally filtered subset.

The active view retains at most 60 consecutive metadata entries. Requests usually align to three server pages of 20; a tall viewport spanning four pages retains partial edge pages within the same 60-entry bound. Its `startIndex` locates that window in the full server result. `loadWorkflowLibraryRange` fetches missing pages, reusing only complete resident page positions from the current list generation while the window is no more than 30 seconds old. Partial reads preserve that conservative window age; only a read of every retained position renews it, including rereads after a changed total. Stale cached views remain ineligible for position reuse until a fresh list read completes, including when revalidation queues behind another filter. Partial edge pages must be read again before extension. Forced Retry and list revalidation read resident positions again. Known mutations immediately disable reuse and fence existing first-page, range and refresh publications before notifying subscribers, even when revalidation queues behind another filter. A changed total detected by a missing-page read also rereads reused offsets. The server supplies no list snapshot version, so concurrent external reorderings still converge through revalidation; newer range requests abort and fence older requests. List revalidation reads the pages intersecting the resident window and retains only its bounded positions; selected metadata is revalidated independently. `selectWorkflowLibraryEntry` selects the freshest matching resident or selected revision from a supplied snapshot, preferring selected state (including errors) at equal revisions. Both enrichment scheduling and the dialog use this policy so detail and preview cannot fall behind selected validation. Invalidation drops enrichment while preserving the selected identity, and only a confirmed removal or access loss clears that pin. Transient failures retain its metadata with a retryable detail error. If deletions move that window beyond the end, it reads the last remaining page. The eight least-recently-used view records retain metadata, totals and one logical scroll anchor per view, with no parsed documents: at most 540 metadata entries across current and cached views, plus one selected entry. Returning to an evicted view starts a fresh server listing.

The grid supplies visible workflow identities before overscan so the 48-identity enrichment bound reaches every visible card even in tall viewports. During restoration, its target rows take that priority until the measured viewport reaches them. Selected detail supplies a separate identity and has priority over visible work. Four workers perform revision-aware raw reads, parsing and requirement extraction. There is no accumulated enrichment queue. Leaving demand aborts work and drops parsed documents immediately; an aborted, obsolete-generation, old-revision or old-account completion cannot publish. Selected detail can retain one document outside the metadata window. Preview owns at most one additional document through its explicit preview request, released after exit or library close. Operations consume documents through their existing operation lifetimes. The raw record cache in `libraryCache.ts` separately retains at most 50 records, validated against list revision and cleared on invalidation/account change.

`src/features/workflow/ui/library/WorkflowLibraryGrid.tsx` virtualizes rows with one to three columns (at least 180 px per card where space permits) against the actual `Scrollable` viewport, measures mounted rows and observes viewport width. The account's view records retain only a server item position and the fraction of its row above the viewport, not row measurement caches. The dialog does not subscribe to anchor changes: each keyed grid reads its filter-owned anchor once at mount, so fractional scrolling does not render the shell or detail rail. A returning grid waits for its actual width before demanding the anchor's range, navigates to that row through the virtualizer, and translates the saved fraction using the resident row's measured geometry. Preliminary top/incorrect-column ranges cannot evict that window. Restoration moves only the grid viewport, never focus; keyboard, pointer or wheel intent cancels it, and filter/account changes or unmount discard it. Narrow dialogs stack the detail rail below the grid, preserving both scroll areas at increased zoom. The viewport is capped at 15 estimated rows even on unusually tall displays, keeping visible rows plus two overscan rows on either side within the metadata bound; one focused/menu row may also remain mounted. Focus pinning retains metadata only; a confirmed local deletion clears the matching pin without discarding a valid off-window focused or menu card. Tab navigation scrolls and refetches the next position before focusing its card/menu control. Matching range requests share transport while their metadata reuse remains fresh; an expired partial flight is replaced by a full read. Each caller checks its own requested positions after settlement; superseded, failed or removed targets do not claim readiness. Focus intent waits for resident metadata and mounted controls, and ends on another keyboard/pointer/focus intent, filter/account change, or unmount. A sticky viewport notice exposes range failures, and explicit Retry revalidates even resident positions. A pinned card's action refetches its metadata position before acting. The project view uses the same virtual rows over its project-owned collection without making library reads. Library selection survives metadata eviction; filters and accounts reset its demand through keyed mount leases. An explicit selection remains preferred when present in the returned view. Otherwise detail selects the first resident entry near the restored viewport, avoiding a page-zero read that would evict its anchor window; per-view selections are not cached.

The owner tests exercise 1,000 workflows with 40 nodes each, repeated view changes, return positions, selected pins and obsolete completions. `getWorkflowLibraryBrowseRetention` exposes deterministic resource counts for that fixture. It does not measure browser heap or production latency.
