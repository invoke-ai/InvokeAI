# Webv2 module architecture

Webv2 uses four top-level module groups:

- `app/` owns providers, routing, boot, and composition roots.
- `platform/` owns application infrastructure with no workbench or feature dependency.
- `workbench/` owns the atomic project aggregate, layout, shell, widget runtime, and extension runtime.
- `features/<domain>/` owns domain behavior behind a small set of public top-level entry modules (`features/<domain>/index.ts` first among them).

Dependency direction is `app -> workbench/features -> platform`. Feature callers import only a feature's public entry modules — the top-level modules each feature registers in `src/architecture/featureInterfaces.ts` (`index` is implicitly public; an unregistered feature or module is private, fail-closed); everything under `core/`, `data/`, `ui/`, and runtime implementation is private. A feature may group substantial behavior under `core/`, `data/`, and `ui/`; pure cores do not import transport, Data, React, or UI modules, including through type-only imports. Production canvas callers use `canvas-engine/api.ts`, not the engine implementation root.

## App and Platform ownership

Ownership is based on invariants, not the first caller:

| Module                 | Owned implementation                                                                                                                                  | Must not own                                                    |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `app/`                 | `main`, provider assembly, routes and guards, route runtimes, adapter selection, cross-module dependency construction, theme/language DOM controllers | Domain behavior, transport implementation, reusable state or UI |
| `platform/transport`   | HTTP primitives and URL resolution, injected auth hook, Socket.IO mechanics, connection snapshots                                                     | Auth token policy, Queue/model/node event interpretation        |
| `platform/state`       | React-free listener/store/selector cores and separate React hook adapters                                                                             | Domain stores or aggregate state                                |
| `platform/query`       | Query client construction and defaults                                                                                                                | Feature query keys, DTOs, invalidation policy                   |
| `platform/i18n`        | i18next bootstrap and supported-language metadata                                                                                                     | Persisted preference ownership                                  |
| `platform/logging`     | Event contracts, recording filters, safe normalization, bounded in-memory history, subscriptions, console output, export envelope                     | Preference persistence, diagnostic presentation, event policy   |
| `platform/ui`          | Chakra system/theme, reusable controls, dialog root and modal presence, toaster, brand mark                                                           | Workbench widgets or feature-specific views                     |
| `platform/runtime`     | Domain-neutral build/runtime metadata                                                                                                                 | Route or feature policy                                         |
| `workbench/backend`    | Queue/node/model progress interpretation and transient domain stores pending their feature migrations                                                 | HTTP, sockets, connection mechanics, generic stores             |
| `workbench/components` | Workbench hydration and Queue progress presentation                                                                                                   | Reusable control or theme implementation                        |

The root of `src/` contains declaration files only. Runtime boot files live in App, the old root entry paths do not exist, and `index.html` names `src/app/main.tsx` directly. `@theme` resolves to Platform UI theme implementation; all other Platform callers use `@platform/*`. No compatibility path exists for moved App, HTTP, socket, external-store, selector, theme, i18n, or reusable-UI modules.

Platform transport receives authentication through `app/main.tsx`, before React mounts: Identity owns the credential and every policy about it, while Platform captures it once per request and reports that request's outcome. The Platform socket publishes raw events and connection transitions; Queue and other domains interpret those events. Lifecycle-specific production composition remains explicit at its natural root: the authenticated socket in `app/router.tsx`, editor runtimes in `app/WorkbenchApp.tsx`, feature UI providers in `app/workbenchPorts.tsx`, and lazy editor bridges beside their lazy entry modules. App constructs the production Queue runtime from Queue, Workbench, Gallery, and Workflow adapters.

Identity holds the tab's bearer token in memory, bound to the account lifetime it authenticates; once that lifetime ends no request can carry it. Each HTTP request captures token and lifetime together, and reports a returned `X-Refreshed-Token` (sliding renewal, or the replacement after the caller's own password change) and any 401 against that capture. Identity accepts a replacement only while the capture's lifetime and token are still current, and a 401 only for the current token, so a late response can neither renew nor expire a newer credential. Renewals replace the token in place: no new lifetime, remount or cleanup, and the media cookie is re-issued at most every five minutes because renewals do not extend it. An own password change runs as a credential rotation scoped to the lifetime that queued it; changes run one at a time, and one still queued when its lifetime ends is rejected unsent rather than dispatched with the next account's credential. Until a rotation settles, other replacements are ignored, and a 401 for the current token or another tab's renewal waits for its outcome, so a delivered replacement supersedes them and a failed change lets them apply; another tab's sign-out applies at once and discards the replacement, because storage cannot tell a deliberate sign-out from any other and a deliberate one must end every tab. The rotation is announced in `localStorage` for its principal while it is in flight, each under its own key so concurrent changes from several tabs never overwrite one another (withdrawn after the replacement is stored, and when the announcing tab leaves or ends its lifetime; announcing also clears markers older than the wait and the single marker earlier builds wrote, whose announcements are not seen during a rolling upgrade), so a tab whose token the change revokes holds the sign-out that 401 would cause, while the request itself still fails to its caller, until the replacement is stored and adopted. This includes a tab whose own concurrent change the other change revoked. The session expires if every announcement of that principal is withdrawn without a replacement, or thirty seconds after the latest one still announced if its tab never settles. A tab restoring or following a token that is rejected under an announced rotation waits the same way and then continues from whatever storage holds. A sign-in attempt leaves the stored token alone until it succeeds. The socket authenticates every connect attempt with the current token and reconnects after the server closes a session whose token was replaced. `localStorage` persists the token across reloads and carries other tabs' changes; it is read when a session resolves and on reconciliation (`storage` events, back/forward-cache restores, returning to view), never per request. Another tab's renewal for the same principal, judged from the token's `user_id` claim, is adopted in place; a removal signs this tab out; any other change ends the current lifetime first and then resolves and activates the new principal like a restored session, the latest stored value winning. A rejected token signs the tab out as expired; an unreachable backend leaves it signed out with the token stored and unobserved, so the next reconciliation retries. Writes this tab made itself are not read back as changes, and blocked storage leaves sign-in working for the tab's lifetime.

Platform State also owns reusable projections of broad external stores into referentially stable read-only stores. App may construct those projections for a feature port, but the listener, caching, and equality mechanics remain domain-neutral Platform code.

Platform Logging is the one recorder for application and project events. `createLogger` binds a source (namespace, area, optional project, widget and operation identity); a runtime passes the account scope it captured so writes after that lifetime are discarded, while module-level loggers stay unbound. Entries are normalized once at ingestion into immutable JSON-safe snapshots: errors keep name, message, stack, cause and status/code, credential-like keys are redacted, URL queries and fragments are stripped, and depth, collection, string and 8 KiB entry ceilings are marked explicitly. History is account-wide and memory-only in three bounded buffers (warn and above, lower severities, timings) so verbose traffic cannot evict problems; closed projects keep their entries until eviction or account cleanup. Publication is coalesced per microtask; clears and account transitions publish synchronously and restore default capture settings. Workbench owns the preference-to-config mapping and the diagnostics panel; App applies saved preferences before React mounts, installs uncaught-error and router catch reporting, and keeps configuration in step with the active account. Each handled terminal failure has one reporting owner: the Workbench store records reported errors, widget failures, autosave outcomes and queue item transitions; the persistence runtime records an exit checkpoint that did not save, since it outlives the editor; transport and coordinator events are debug breadcrumbs.

`pnpm architecture:check` is the executable source of truth for these dependency directions. It uses the TypeScript parser to classify static imports, type imports, dynamic imports, re-exports, and inline imported types after resolving aliases and relative paths. Temporary violations must be recorded in `src/architecture/migrationExceptions.ts` with an owner and a removal ticket; architecture completion requires that registry to be empty.

The queue pilot is the first migrated feature. Its private `QueueBackendPort` is the adapter seam; public callers use domain reads, commands, and production runtime factories from `@features/queue`. Private snake_case HTTP DTOs map explicitly to camelCase Queue read models before crossing that interface. TanStack Query owns the global backend queue read model, which reads and hydrates only a bounded recent window, and a status-only read for count summaries such as Home; non-React runtimes own reconciliation and realtime orchestration. Persisted per-project queue history remains in the Workbench aggregate.

Queue exposes board-independent active backend sessions, including preparation and result settlement. The Gallery progress section includes every unfinished batch slot, including queued work; Preview follows executing and settling sessions. Both use gallery-destination projections of the active project's queue; eligibility is presentation policy, separate from discovery. Workbench owns transient overview/pinned follow selection for its mounted lifetime, clears pins on project changes or when following stops, and never persists pins or preview frames. Live sessions do not participate in board counts, saved-image selection, or navigation. Saved outputs retain their actual backend board destinations; automatic result selection does not change the browsed board or its paging window.

Intermediates owns the manager for temporary media behind `@features/intermediates`: transport mapping, account-fenced query keys, the selection core, the confirmation dialog and the operation panel. It is a Settings section, contributed as metadata through `settingsContribution` so the dialog's catalog never loads the manager or its transport until the section opens. The eligibility policy (safe, referenced, active, recent) is server-owned; the manager requests a server preview, which fixes the instant recency is judged at and describes what a cleanup would delete and keep, and confirms it once. "All matching" selections travel as a `matching` scope carrying the summary's filters and the excluded rows, which the server resolves; the client never enumerates pages it has not loaded. Operations are not persisted by the server: a manager that opens with nothing followed lists the account's operations and follows the newest unfinished one, so a reload picks a running cleanup back up, and a settled operation that left failures behind offers to delete its scope again. The client's one input to the policy is a browser hold lease: `holdLease` (a public entry, started by Workbench for the provider's lifetime) keeps the media open editors still need (live content from every open project plus the undo state each live Canvas engine retains) classified as active. Workbench owns the name set: `projects/projectAssets` scans each immutable project subtree once, and each Canvas engine registers its retained undo state with the mounted Workbench, which re-reads it when the history changes; an engine released by one Workbench is replaced, not reused, by the next, and one another Workbench still uses is refused. The lease is one per tab, holding up to the server's per-kind limit of sorted unique names, which the server replaces atomically; it skips unchanged sets without re-serialising them, forgets a send the server did not acknowledge so the next change, heartbeat or return to the foreground sends again while the previous lease still stands, refreshes every five minutes and when a tab becomes visible after missing a refresh, and releases with `keepalive` on dispose and `pagehide`; the server keeps at most eight leases per account and expires a lease after 15 minutes, which bounds anything a crash leaves behind. Realtime updates attach for the section's mounted lifetime through the Platform socket hub and invalidate the account's summaries when an operation settles, by either the socket or the polled record, or when the socket reconnects. Workbench supplies the entry points (the Data & workspace link, the project actions menu, the Users page callback) and hands the manager a one-shot focus intent (a project to preselect or an account to filter by) rather than route state.

Fonts owns its authenticated catalog, managed-library UI, and browser font-registration lifetime behind `@features/fonts`. App composes the session runtime; Canvas receives a font-resolution port and owns text geometry, rendering, and output readiness. Persisted text references and project-file remapping remain in Workbench. Launchpad font previews and Canvas share the same account lifetime; font binaries and browser registration names are not project state. The browser registry admits at most 64 faces and 128 MiB of font input data, including faces currently being parsed. Active references are protected from eviction; if they exhaust the budget, further loads fail until references are released. This bounds retained input, not browser-specific decoded font memory. Canvas reconciles active references only when the document forests or text draft source change.

Font runtime composition and project-file option state travel in the existing shared route chunk. Catalog transport, the Fonts page, and project-file option dialogs load on demand. Missing-font recovery loads only for documents containing custom references. The locale asset plugin serves font-library strings as a separate namespace in development and production, loaded when the library or recovery UI opens; source translations remain in the canonical locale files. Text tool controls load when selected; their shared Canvas/Layer form and interaction dependencies remain grouped to avoid extra widget-activation requests. Catalog query keys have a lightweight public entry so invalidating an imported font does not pull the transport into startup.

Projects own their workflows. The Workbench aggregate keeps an ordered workflow collection with an active selection and one session edit history per workflow (`src/workbench/projectWorkflows.ts`); the project document is schema 3 and `migrateProjectDocument` in `projects/projectDocument.ts` is the single migration boundary for older documents. Workflow reads the active workflow through the App-composed port and edits, publishes and presents documents; it never replaces authored project work. The library is written only by the Workflow-owned publication controller, which captures the account, project, workflow and content before it starts, refuses to overlap itself per workflow, reconciles a lost answer against the destination record before resending, and records the resulting library id and revision on the originating workflow alone. Queue submissions carry the originating project workflow so seed advances, node progress and run previews return to it whatever is active later.

Workbench persistence follows the same lifetime rule. `createWorkbenchPersistenceRuntime` owns hydration ordering, debounced autosave, hidden-page saves, revision/generation checks, conflict application, reconnect replay, status publication, and the exit checkpoint without importing React. `createSyncedWorkbenchPersistence` constructs the local/remote project synchronization state for one mounted Workbench; no process-wide maps, sets, flags, or caches hold that state. It also owns the unload journal: the runtime asks it, through its persistence port, to journal unsaved state synchronously when the page is hidden or unloads, and its load reconciles the journal into the draft store under the draft store's fencing rules. `WorkbenchProvider` constructs these lifetimes, starts the runtime and ends it with its exit checkpoint through the mount lifecycle adapter, and selects aggregate hydration state. The checkpoint and the persistence lease outlive the unmount until it settles. The provider also hands the checkpoint to the account lifetime's next editor through a module-level map keyed by the account scope, and that editor loads after it, waiting at most 10 seconds; the tab's editor session is reference-counted across the two. See `workbench/projects/README.md`. Project transition commands commit pending editor drafts themselves, so callers do not flush before creating, opening, switching, or closing a project.

## Contract ownership

Contracts live with the module that owns their invariants. The retired `workbench/types.ts` path is an architecture violation; Workbench aggregate, widget, Canvas, persistence, settings, and feature contracts each have an owner-local canonical path. Persisted schemas and backend DTOs remain private versioned/wire values and cross seams only through explicit serializers, hydrators, or mappers.

`platform/core/outputImages.ts` is the explicit shared adapter for backend invocation-output image names. It is platform-owned because Queue and Nodes both need the projection and cannot import each other's private implementations. The adapter recognizes only the backend's direct image, image-collection, and workflow-return output contracts; it must not become a recursive walker for arbitrary metadata or input fields.

Feature callers import a feature's public entry modules; imports of another feature's `core/`, `data/`, `ui/`, or runtime implementation are rejected outside a ticketed migration exception. Wildcard exports may aggregate files inside one owner, but may not cross an ownership seam. The contract caller matrix and development-invalidation budgets are generated by `pnpm architecture:check` and `pnpm test:performance:build` respectively.

The byte budgets in `performance/architecture-baseline.json` and `performance/browser-baseline.json` record measurements only. Each byte ceiling is the lower of `max(1%, 4 KB)` over the **higher of the base reference and committed measurement**, and `max(10%, 32 KB)` over the committed measurement (`deriveLimit` in `scripts/performance-budgets.mjs`). Deliberately re-recording a higher baseline therefore accepts reviewed growth, such as a dependency upgrade, in the same PR. Growth beyond that allowance still fails. Previously recorded higher measurements remain accepted until a downward re-record protects the savings; the committed hard ceiling continues to bound cumulative growth in the base branch. Re-record with `pnpm test:performance:build:update-baseline` and `pnpm test:performance:browser:update-baseline`, and include the measured cost or savings in review.

CI restores `main`'s own measurements from the Actions cache (`WEBV2_PERF_REFERENCE_DIR`) for pull requests into `main` and merge groups targeting `main`. Logs and reports name the restored reference. Local runs, pushes to `main`, and stacked PRs without a reference compare against committed measurements directly. Source-owner sets stay pinned exactly in every mode: a module entering a route's initial graph fails at zero bytes. Request counts carry no allowance and remain capped at the lower of the reference and committed counts. A byte rebaseline does not relax request counts, source ownership, inactive-widget loading, or other structural checks.

Compatibility exports under `workbench/` are temporary. New behavior belongs behind the target module interface and compatibility files must not acquire new implementation logic.

## Widget placement and floating windows

A project places each widget instance in regions (`widgetRegions`) or in a floating window (`floatingWidgets`), never both. `workbench/floatingWindows.ts` owns the rules; the reducer, placement normalization, and the rails all read placement through it.

- **A floating instance belongs to no region's `instanceIds`.** Floating removes every membership, repairs the active selections it leaves behind, and records one return destination (`returnRegion`, `returnIndex`).
- **A return region keeps a marker for each of its windows.** `getRegionOrder` is the region's complete order — docked members plus markers — and a marker's `returnIndex` is its position in it. Docking counts the docked members ahead of the marker, so docking in any order never moves what the rail shows. Reducer edits that add, remove, or move members go through that order so the indices stay in step; reordering docked members fills the docked positions around stationary markers.
- **Empty-center recovery is the one exception to origin-only docking.** A center emptied by a float keeps naming the instance in `activeInstanceId`. While it is still empty and still names that instance, Dock restores center membership along with the origin, and Remove restores center membership only (no rail slot, no panel). No extra field is persisted; a center that has gained a view or changed its pointer is left alone. "Empty" means no members at all: the reducer has no widget registry, so a center left holding only a disabled or unregistered view is not recovered and shows that view's unavailable state until another view is chosen.
- **An instance opened in the center is shown once.** It may stay a member of a side panel, but a left or right panel fronting it fronts its next member instead, or collapses when it holds nothing else. Only the pointer moves, so a hidden panel stays hidden. The bottom region is left alone: the reducer has no registry to tell its panels from tooltip-only status items. This is what lets every "open in Preview" path, and the center Preview toggle, reuse the Preview a rail holds.
- **Region requests never discard a window.** Selecting, moving, or reordering an instance a region does not hold is a no-op, and so is enabling an instance that floats. Opening a widget type whose instance floats restores its return placement first, then opens the requested one, and auto-routes once.
- **One normalization.** `normalizeFloatingPlacement` runs on project hydration, on stored presets, on preset application, and inside preset comparison (which includes `returnIndex`), so an applied preset always matches the snapshot it came from. It is idempotent. Indices stored before markers were counted are read deterministically (ascending, ties by instance id, missing ones appended); that is best-effort and does not reconstruct the original arrangement.

- **A closed window leaves its geometry behind.** When a window closes — docked, removed, or closed by a preset or an undo — its position and size move to `Project.lastFloatingGeometry` (`rememberClosedWindows`); floating the instance again takes them back out and reopens the window there, windowed, and only a first float cascades. The float command passes the viewport, so a rectangle remembered in a larger one is brought wholly on screen rather than reopening as a sliver. The memory holds only instances that exist and are not floating now, in every state the reducer produces, so a save is exactly what a load reads back. It is persisted with the project and validated on load, but it is not layout: preset snapshots, drift comparison, and undo snapshots do not carry it.

- **Each preset keeps its working arrangement per project.** Switching away stores the outgoing arrangement in `Project.presetWorkingLayouts` when it differs from the saved preset, and switching to a preset lays out its copy there when it has one, else the saved snapshot. The copies are an ordered list, oldest first, with at most one per preset and at most 16 (the oldest goes first). Each is a `LayoutPresetSnapshot` (placement, panels, center view, instance identity and title — never widget state) and never names the active preset: the live layout is its copy. Opening or hydrating a project drops copies of presets the account no longer has and copies equal to their saved preset, and every switch drops the former, so orphans never hold one of the 16 places; deleting a preset drops its copies from every open project, and a project that was on it moves to the default preset the way a switch would. A renamed preset keeps its id and its copy. Save on the active preset writes the live layout; on another preset it writes that preset's copy to the account and leaves the copy in place, where it no longer reads as unsaved because it equals the saved preset, so a lost account write still leaves the arrangement recoverable until hydration proves the copy redundant. Saving a preset also drops every other open project's copy of it that equals its previous or its new saved arrangement: such a copy was no change of that project's own, and kept it would show the outdated arrangement as unsaved and could overwrite the newer save. Revert on the active preset reapplies the saved snapshot, as choosing the active preset again does; on another it drops the copy as an undoable step. Pressing the active tab while a cold switch is still loading cancels that switch instead. Saving the arrangement as a new preset moves the project onto the new preset. Copies are persisted, validated on load like stored presets, and captured in undo snapshots with `layout.presetId`, so undoing a switch restores both.

The rails subscribe to placement only (`getWidgetPlacementProject` projects `floatingPlacements`), so a window's geometry, mode, and stacking change without re-rendering them. A marker is not a tab: it stays out of the sortable list, activating it raises and expands its window, and Dock and Remove live in its context menu. Marker UI exists only on the left and right rails.

### Focus

Workbench focus is transient and never persisted. `WorkbenchFocusProvider` (`workbench/WorkbenchRuntime.tsx`) owns one controller (`workbench/focusRegions.tsx`) above the UI ports, the hotkey runtime, and the shell; there is no module-level focus state. The target is a docked region or one floating instance.

- **Keyboard navigation.** `Alt+Shift+Arrow` (`Ctrl+Option+Arrow` on macOS, where Option+Shift+Arrow selects text by word or paragraph and Ctrl+Arrow chords belong to Mission Control) moves focus to the nearest visible docked region in that direction, using current frame geometry and preferring alignment; without a current target it enters the center. It preserves widget selections, skips hidden regions, and stops at the edge. From a floating window, its center is the starting point on the movement axis so overlapping docks remain reachable; when no dock lies beyond it in that direction, focus returns to the dock underneath its center. `Alt+PageUp` and `Alt+PageDown` cycle the focused docked region's enabled panel views in placement order, wrapping at either end and focusing the owning region once the selected instance is visible. Side frames wait for their lazy view to load; the persistent center frame can take focus immediately. Toolbar, tooltip, popover, and floating placements are excluded; a single eligible widget stays open. All six commands are customizable in Hotkeys settings, work from editable fields (their defaults are chords no text field binds on that platform), and respect modal suspension. Ordinary Tab and arrow-key handling is unchanged.

- **One judge of the target.** `getTarget()` returns the target only while it describes something on screen: set under the current project and account, and — for a window — still floating. The provider also clears eagerly when the active project changes, the account changes, or the workbench unmounts; that is what notifies subscribers and abandons a focus move still waiting for its widget to mount. Returning to a project never brings old focus back.
- **Activation.** Pointer-down and keyboard focus activate a region or window; hover does not. The active window carries the same accent outline, under the same preference, as a focused region, and no region is outlined while a window is active. A window passes the project id it was rendered for, so a late event from a project that has left the screen is refused before it can raise anything.
- **Raising.** A press inside a window always asks the reducer to raise it, which is a no-op for the topmost window. Focus raises a window only when it makes that window the active one: focus moving around inside the already-active window, or returning from a closing dialog or popover, writes nothing. Ordinary focus leaves a shaded window shaded; the explicit reveal (marker, center "Show window", recall) expands it.
- **Recall is the one reveal that moves no focus.** A recall raises and expands its window but leaves keyboard focus, the outline, and the hotkey target where the user had them; the next press or focus change brings them back into agreement. Because focus inside the active window does not re-raise, it cannot re-bury the window a recall just revealed.
- **Keys follow the outline.** A press inside a window moves keyboard focus into it when focus was elsewhere, and a press on a docked region pulls focus out of a floating window. The floating layer renders windows in a fixed DOM order and stacks them by z-index alone: raising a window never moves its node, which would drop the focus that raised it.
- **Focus follows placement:** into the window after Float and after a marker or "Show window" reveal, into the region a docked rail tab shows in when it is selected, so keys stop going to a window that held them, into the return region after Dock, and after Remove from a marker's menu into the center when it gets its view back, otherwise into the panel the window's own rail is showing — or the center when that rail shows none, emptied by the float or collapsed. Removing a window from a rail's enable menu moves no focus: that menu stays open and keeps it. A focus move targets the region frame that is on screen (side regions keep earlier panels mounted but hidden), waits a bounded time for its widget to mount, and is abandoned if the user presses somewhere else first. Every panel frame carries its instance's identity, including the stand-in for a widget whose view cannot render, so a move into it lands.
- **Hotkeys read the same target.** `HotkeyContext.focusedRegion` is `WidgetRegion | 'floating' | null`; the persisted `WidgetRegion` is unchanged. A key press is aimed at the widget under the event target first and, outside any widget's DOM, at the active floating instance or the focused region's active member (`resolveHotkeyTarget`). A region's active pointer counts only while it names a member, so a view that floated out of an emptied center answers as a window, not as the center. A floating command source carries `region: 'floating'` and is never used to index `widgetRegions`. Generic `focused-region` shortcuts match under a window, shortcuts tied to a named docked region do not, and a floating widget's own `focused-region` contribution follows its window at the same priority it has when docked.
- **Modal dialogs suspend application shortcuts.** Every dialog is built on the Platform `Dialog` root (`platform/ui/Dialog.tsx`; lint rejects Chakra's dialog and its drawer, which has no such root yet), which registers with `platform/ui/modalPresence` while its own open state holds, unless it is declared `modal={false}`. A dialog whose module is still loading uses `Dialog.Pending` as its suspense fallback, so it is modal from the keypress that opened it. While any registration stands, the hotkey runtime runs only hotkeys marked `allowInModal` — the command palette toggle — so invoke, global and widget shortcuts stay inactive wherever focus is, and keys the dialog handles itself (Enter, Escape, typing) keep their browser behavior; the Canvas engine's own key listener takes no key either. Both ask about the key press they are handling: a press that began under a modal still counts as aimed at it, because the Escape that dismisses a dialog releases its presence before the same press reaches bubble-phase listeners. Presence follows interactivity, not DOM: a closing dialog that stays mounted through its exit animation is inert and releases at close, so the next press reaches the application; reopening re-registers at once, an outer dialog stays registered while an inner one closes, and an unmount releases without a close. Media paste reads the same presence. Popovers and menus do not register.

### Contextual shortcut guidance

Shortcuts is a bottom-only popover widget. Built-in layouts put it on the right immediately before Notifications; saved and custom layouts retain their placements and can enable it through Bottom Widgets. The whole chip opens its guide, and normal widget controls own reordering, alignment, visibility and dismissal. Its `compactSizing` metadata asks the status-bar host for remaining capacity: the host observes its strip, two clusters and spacer, while the guide measures only its own keycaps. Up to four whole hints fit without increasing the status bar's height; a keyboard icon retains access when no hint or label fits. If all relevant bindings are unassigned, the popover explains that state and provides keyboard shortcut settings.

The Workbench focus lifecycle also owns the transient hint-source registry and last editing element. A keyed Canvas registration mounts one stable source for its project/instance engine lease; changing generation/staging locks publish through a boolean-filtered project subscription rather than replacing that source. Lock reads cache the document revision, staged-candidate array and queue-item array; unrelated project updates do not rescan queue work. The lock predicate tests candidate presence and active work without constructing staging slots. Narrow tool/session subscriptions cache scalar hint inputs; the guide never acquires an engine lease or imports property forms. Sources are fenced by project and instance and released with their owner. Project/account changes clear the editing origin. The widget's `preserveWorkbenchFocus` metadata keeps its compact chip and portal from replacing that origin; closing returns focus there. Guide activation and Escape do not reach Canvas session handlers; configured global chords keep their normal runtime handling.

Command hints resolve against the runtime catalog and mounted extension contributions, including custom bindings, scope conflicts, editable fields and modal exclusions. Command bindings reserved for guide activation or dismissal (bare Enter/Space and Escape chords) are omitted in favor of a usable alternative; fixed Canvas instructions may still describe those keys. Fixed gestures remain Canvas-owned and distinguish selection modifiers at the press from constraints during the drag. Properties shows them as “On Canvas”; active modal presence hides the background guide. Pointer coordinates and pixel epochs are not hint subscriptions.

### Window interactions

- **Geometry is stored once and adapted in CSS.** Every window shares one static rule set; the stored geometry and stacking rank arrive as inline custom properties (registered as non-inheriting, so a drag restyles the window and not the widget inside it), so a commit changes values rather than minting a class. The position keeps a 48px sliver reachable (`FLOATING_VIEWPORT_MARGIN_PX`, the same margin `clampWindowToViewport` applies to commits) and the displayed size is capped to the viewport. A viewport that shrinks therefore persists nothing; the stored geometry applies again when there is room.
- **Gestures start from the rendered rectangle**, not the stored geometry, so a window CSS is clamping or capping does not jump. A gesture commits only what it changed: a move keeps the stored size, and a resize keeps the stored values of any axis it did not change (`commitResizedAxes`), because what is on screen there may only be the viewport's clamp or cap. The viewport clamp applies to the changed axes alone, so a vertical resize never rewrites a stored x, nor a horizontal one a stored y. A press that never moves, or a drag against the minimum or the cap, commits nothing. Keyboard steps follow the same rules.
- **One commit per gesture.** Pointer moves are coalesced to animation frames and previewed as inline custom properties on the window element; the store is written once, when the gesture ends — on release, or when the pointer is taken away (`pointercancel`, a release the page never saw), which keeps what was dragged so far. Escape discards the preview. Each keyboard step is its own commit.
- **Resize handles.** Eight pointer-only handles (four edges, four corners) straddle the border with matching cursors and non-overlapping hit areas, above an isolated content frame so widget stacking cannot cover them. Inside the bottom-right corner sits the `ResizeCorner`, the single labelled, keyboard-operable resize control; the pointer-only handle there is clipped to the band outside the border. That control announces the size on screen — the stored size as the viewport caps it — and follows the viewport, so its value and its keyboard steps agree. `resizeFloatingGeometry` anchors the opposite side, holds the size between the minimum and the viewport (a viewport smaller than the minimum lowers it to the viewport, so the shown size is not mistaken for a resize), and stops the top edge at the viewport's top.
- **One gesture path.** The title bar, the grip, and every handle start through the window's single pointer session, so a new gesture replaces the one before it and resize gestures all raise the platform's resize-drag signal. The preview names the mode the gesture began in and applies only while the window is still in that mode: a window that maximizes or collapses under a gesture shows its new frame at once, and the gesture ends itself — releasing the drag cursor and committing nothing — the next time it hears from the pointer. Docking, removing, or switching project unmounts the host (hosts are keyed by project and instance), which aborts the session.
- **Title bar.** Double-click maximizes or restores, and expands a collapsed window; Restore returns to the windowed geometry, which maximizing never touches. Collapse and Expand are explicit buttons. The label truncates first, down to its icon; contributed widget actions then give way in a strip that scrolls, without a scrollbar, by focus, a sideways scroll, or touch, so a focused action is always in view with its ring; the window's own controls never shrink.
- **Shaded bodies stay mounted.** A shaded body is hidden with React `Activity`, so its local state survives and no second copy mounts. Drafts are flushed before shading, docking, and removing, because hiding or unmounting an editor stops its flusher.

## Settings contributions

Settings are declared by their owners and presented by Workbench. Platform UI owns domain-neutral field metadata and controls; it does not own setting values or persistence. A widget manifest exposes a `settings` contribution containing localized field metadata, an ordered `quick` subset, and a deferred field binding loader. The full dialog includes every declared field. Bindings retain the owner's normalization and command path, including Gallery's size/density conversion and project/instance fencing.

Workbench composes widget and application contributions into a metadata-only catalog. Search, dialog navigation, quick popovers, and command-palette destinations share that catalog. Features publish contribution metadata through registered public entries; loading metadata must not load their UI or start data queries. Application-owned additions can join a widget section without changing the owner of their values. Deferred resources cache code only; field subscriptions exist only while their controls are mounted.

Section placement does not determine storage lifetime. Account/install preferences, project settings, widget-instance values, and server configuration retain their existing persistence and authorization. Each surface lists only settings it can edit: the Launchpad Preferences page leaves out project and widget settings, and the workbench dialog leaves out widget settings for widget types the open project lacks. The shell resolves explicit project/instance targets and disposes target-bound editing when projects change. Owner bindings fence writes against stale account/project lifetimes.

The settings host owns the dialog's presence lifecycle and keeps its root mounted through closing. The body is deferred until first opening, remains present during exit, and unmounts afterward. Quick-popover handoff carries both the instance target and the original gear for focus restoration.

Before section navigation becomes available, the deferred dialog prepares binding/editor code without mounting editors or starting their queries. Section and scroll position survive closing within the account lifetime. The shell renders a shared modified-setting indicator; bindings determine whether a value differs from the owner’s canonical default. Quick settings use the shared arrowed popover with an inner scroll area, and dialog selects keep their bounded scroll areas inside the modal focus scope.

Production chunking keeps the catalog and manifest metadata separate from editor boot UI. The build gate checks that Launchpad’s palette and settings dialog do not statically include the editor application or widget renderer. Shared settings controls remain in the common UI chunk; owner field bindings and custom editors remain deferred.
