Upgrading an existing install to v7 is one-way. This page covers what the upgrade changes, where the backup of your database is, how to go back to an older version, and how to try v7 without touching your current install.

## The upgrade is one-way

The first time v7 starts on an existing install, it updates the database at `<root>/databases/invokeai.db` in place. After that, older versions cannot use it:

- v6.14 and later, and earlier v7 builds, stop at startup with an error that begins `Database contains unknown applied migration IDs`.
- v6.13 and earlier do not recognize the update. They may start and report the database as up to date, but they then run on a database they were not written for, where they can misbehave or damage it.

Restore a backup before you run any older version on this install.

The update changes the database only. Your images in `outputs/` and your models are left as they are.

## Backups

Before every update of the database, Invoke copies it to a backup in the same folder, `<root>/databases/`:

```text
invokeai_backup_<YYYYMMDD>-<HHMMSS>.db
```

When two backups are made in the same second, the later one gets a number, e.g. `invokeai_backup_20261019-093000-1.db`. Before the update, the startup log shows a warning that names the backup:

```text
Updating the database at <root>/databases/invokeai.db. Older versions of InvokeAI cannot use it after this update. Its current state is backed up to <root>/databases/invokeai_backup_20261019-093000.db; ...
```

Invoke never deletes backups. Delete old ones yourself once you no longer need them.

### Which backup to restore

To go back to v6, restore the backup written when you **first started v7**. Its date and time, in your computer's local time, are those of that first start. It holds your database as v6 left it.

- **Not the oldest backup.** v6 writes backups with the same name when it updates the database itself, so the oldest file is an older v6 state, without your work since then.
- **Not the newest backup**, unless you have started v7 only once. Each later v7 update writes another backup, of a database v6 cannot use.

The warning in the log of that first v7 start names the right file.

Nothing you did in v7 after that start is in the backup. Images you generated in v7 stay in `outputs/`, but v6's gallery does not show them. Models you installed in v7 stay in the models folder, but v6's model list does not have them.

:::caution[Models installed in v7]
v6 lists the models you installed in v7 as orphaned, and its **Sync Models** in the Model Manager offers to delete them. Keep them if you may go back to v7: the v7 database you set aside, `invokeai.db.v7`, still uses them.
:::

### MySQL and MariaDB

Invoke makes no backup of a server database. Back it up yourself before upgrading, as [MySQL and MariaDB](/configuration/external-database/) describes. To go back, restore that backup.

## Restore a backup

<Steps>

1. Stop Invoke.

2. Open the `databases` folder in your root directory.

3. Move the current database aside: rename `invokeai.db` to `invokeai.db.v7`.

4. **Required:** if `invokeai.db-wal` or `invokeai.db-shm` exist, rename them to `invokeai.db.v7-wal` and `invokeai.db.v7-shm`. Left in place, the v7 database's write-ahead log would be applied to the restored file and could corrupt it. Renamed this way, the three files stay a complete copy of your v7 database.

5. Copy the backup you chose to `invokeai.db`. Copy it rather than rename it, so the backup stays as it is.

6. Start the older version.

</Steps>

Steps 3 to 5 as commands, with your root directory and the backup's name filled in:

<Tabs syncKey="operatingSystem">
  <TabItem label="Windows" icon="seti:windows">
    ```ps
    cd <root>\databases
    Rename-Item invokeai.db invokeai.db.v7
    if (Test-Path invokeai.db-wal) { Rename-Item invokeai.db-wal invokeai.db.v7-wal }
    if (Test-Path invokeai.db-shm) { Rename-Item invokeai.db-shm invokeai.db.v7-shm }
    Copy-Item invokeai_backup_<YYYYMMDD>-<HHMMSS>.db invokeai.db
    ```
  </TabItem>
  <TabItem label="Linux/MacOS" icon="linux">
    ```bash
    cd <root>/databases
    mv invokeai.db invokeai.db.v7
    if [ -e invokeai.db-wal ]; then mv invokeai.db-wal invokeai.db.v7-wal; fi
    if [ -e invokeai.db-shm ]; then mv invokeai.db-shm invokeai.db.v7-shm; fi
    cp invokeai_backup_<YYYYMMDD>-<HHMMSS>.db invokeai.db
    ```
  </TabItem>
</Tabs>

## Run v7 alongside v6

Each install's root directory holds its own database, images and models. Give v7 a root of its own, and your v6 install stays as it is. The v7 install starts with an empty gallery and no models.

- **Launcher:** install v7 into a new, empty folder. Do not select your existing install: that upgrades it in place. The folder you install into is v7's root directory.
- **Manual install:** install v7 into a new directory, as [Manual Installation](/start-here/manual/) describes, and start it with `--root` set to that directory, or set the `INVOKEAI_ROOT` environment variable. `--root` takes precedence over `INVOKEAI_ROOT`, which takes precedence over the directory of the active virtual environment; see [InvokeAI Root Directory](/configuration/invokeai-yaml/#invokeai-root-directory).

:::caution[Keep the models folders apart]
Do not point both installs' `models_dir` at the same folder. Each install knows only the models it installed itself, so **Clean up orphaned models** in one install's Model Manager lists the other install's models as orphaned and offers to delete them.
:::
