Every image and video InvokeAI produces carries its generation record **inside the file**, so a
download dropped into any Invoke instance is recallable and remixable without access to the
database that produced it. This page is the reference for that contract: where the record lives
in each container, the record's fields, and how the format evolves.

## Envelope: shared keys and image inputs

Three keys are shared by images and videos. Images generated from a graph also carry a
separate resolved-input record. Values are JSON strings; saved workflow JSON retains its original bytes.

| Key | Content | Required |
|---|---|---|
| `invokeai_metadata` | The generation record (schema below) | when the graph produced one |
| `invokeai_workflow` | The `WorkflowWithoutID` the session ran, verbatim | only when a workflow was run |
| `invokeai_graph` | For generated images, the complete session source `Graph`; videos retain their existing graph record | when available |
| `invokeai_resolved_inputs` | PNG only: compact Graph JSON containing the active invocation's resolved inputs and ordinary ancestors | images generated from a graph |

| Container | Where the keys live | Writer | Reader |
|---|---|---|---|
| PNG | `tEXt` chunks, one per key | `DiskImageFileStorage.save` via Pillow's `PngInfo` | `extract_metadata_from_image` reads `Image.info` |
| MP4 | QuickTime keyed metadata: `moov/udta/meta` with an `mdta` `keys` table and `ilst` UTF-8 `data` atoms | `DiskVideoFileStorage.save` remuxes through the bundled ffmpeg (`-movflags use_metadata_tags`, stream copy, `+faststart`) | `invokeai.app.util.mp4_metadata.read_mp4_tags`, a pure-Python box walk |

Both readers feed `extract_metadata` in `invokeai/app/api/extract_metadata.py`, which owns the
validation rules: the metadata must parse to a JSON object, the workflow must validate as a
`WorkflowWithoutID`, and the graph must be an object with a `nodes` object and an `edges` list.
Anything else degrades to "absent". The image reader additionally extracts optional
`invokeai_resolved_inputs` using the same graph envelope checks, preserving the JSON string verbatim.
These checks accept unknown community node types and unset connected fields without loading node schemas.
A missing or malformed resolved-input record is ignored independently of the other channels.
On image upload, the file is fully decoded in a worker thread before reading records, including
PNG text chunks after IDAT. Records are extracted before cropping or resizing can discard `Image.info`
and passed explicitly to the image service for persistence. A client-supplied `metadata` form field wins
over the embedded copy; workflow, graph, and resolved inputs are never client-overridable.

When workflow JSON is absent, the image editor converts `invokeai_graph` into an editable
workflow. Keeping the source graph preserves original `Iterate`, `If`, and `Collect` nodes
and their edges. `invokeai_resolved_inputs` is a separate PNG text chunk, exposed as optional
`resolved_inputs` stringified Graph JSON in `GET /api/v1/images/i/{image_name}/workflow`. Inspection
can prefer this record to display actual inputs, while `workflow` and `graph` retain their original
contents for editor restoration. The route applies the same image read-access and storage-maintenance
checks to all three fields. Older PNGs return `resolved_inputs: null`; responses that omit the field
remain valid. Videos use the shared response model's `null` default and retain their existing metadata
behavior. Shared metadata extraction and the MP4 reader retain their three-key contract; only the
image reader fills the optional resolved-input field. The new response field does not
reserve or replace any key inside user `invokeai_metadata`. No migration is needed.

The resolved-input record includes ordinary ancestors, such as math nodes and a Noise node's
actual seed, and stops at loop/control and collection boundaries. Values crossing those
boundaries are already resolved on the retained downstream invocation. Each image stores one
source graph plus this record, avoiding copies of the expanded runtime graph in nested batches.
Literal collections in the source graph and collection inputs on retained invocations still
contribute their full size; neither graph field is guaranteed to contain a single node.

The MP4 layout is the one `ffprobe`, `exiftool` and `mediainfo` display. Like PNG chunks it
survives a container-aware copy — for ffmpeg that is a remux with `-movflags use_metadata_tags`;
a plain `-c copy` or a re-encode drops it.

:::note[Videos stored before embedding]
Videos saved by earlier releases keep their record in a JSON sidecar under
`outputs/videos/sidecars/`. The reader consults the MP4 first and the sidecar second; the sidecar
is also the fallback written when the remux fails, so a record is never lost to ffmpeg.
:::

## The record: `invokeai_metadata`

A flat JSON object emitted either by the `core_metadata` node (in linear/canvas graphs) or directly by any denoise invocation (`*denoise*` nodes inherit `WithMetadata` and emit `metadata` on their output, merging any upstream `metadata` input with the node's own sampling, model, LoRA, and adapter fields via `build_denoise_metadata`). Custom node workflows can wire a denoise node's `metadata` output straight into the decode (`*_l2i` / `*_latents_to_video`) node without a `core_metadata` node. Video is a *profile* of the same
record as images, discriminated by `generation_mode`, not a second format. Every key is
optional; readers ignore keys they do not know and never reject a record for having them.

Common shapes:

```
ModelIdentifier = { key, hash, name, base, type, submodel_type? }
ImageRef        = { image_name }
VideoRef        = { video_name }
LoRA            = { model: ModelIdentifier, weight }
H3Reference     = { kind: "image" | "video", image_name?, video_name?, detail?, conditioning?, start_frame?, end_frame? }
```

### Versioning

| Key | Type | Meaning |
|---|---|---|
| `metadata_version` | semver string | The record schema version, currently `1.1.0`. Absent on records written before versioning; they are read with the same rules plus the aliases listed below. |
| `app_version` | string | The InvokeAI release that wrote the record. Informational. |

The version is over the **record**, not the node that writes it. A **minor** bump adds keys or
widens a value set: any 1.x reader parses any other 1.x. A **major** bump renames, removes or
retypes a key. Readers are tolerant by construction: they read the keys they know, ignore the
rest, and never reject a record for its version, so a newer record still recalls what it can.
The current value is `CORE_METADATA_VERSION` in `invokeai/app/invocations/metadata.py`.

### Shared with images

| Key | Type |
|---|---|
| `generation_mode` | string. Video values: `wan_t2v`, `wan_i2v`, `wan_interpolate`, `wan_extend_video`, `minimax_h3_t2v`, `minimax_h3_i2v`, `minimax_h3_lf2v`, `minimax_h3_flf2v`, `minimax_h3_extend_video`, `minimax_h3_ref2v`. A record is video metadata iff this is one of them. |
| `positive_prompt`, `negative_prompt` | string; `negative_prompt` is absent for MiniMax H3, which has no CFG |
| `seed`, `steps` | integer |
| `cfg_scale` | number (Wan only) |
| `width`, `height` | integer |
| `model` | `ModelIdentifier`: the main (transformer) model |
| `vae` | `ModelIdentifier`: a standalone VAE override |
| `loras` | `LoRA[]`: the LoRAs the graph loaded, in order; absent when none ran |

### Aliases read for pre-1.0 records

Earlier writers spelled three Wan keys differently. Readers accept both spellings; the current
graph builders write only the canonical ones.

| Canonical | Also read as |
|---|---|
| `wan_guidance_scale_low_noise` | `guidance_scale_low_noise` |
| `wan_t5_encoder_model` | `wan_t5_encoder` |
| `wan_transformer_low_noise` | `transformer_low_noise` |

## What a recall can restore elsewhere

- **Models** in a video record resolve against the local catalog by `key`, then by `hash`, then
  by `name` + `base` + `type`. Keys are minted per install, so a record that travelled with a file
  names keys the receiving catalog has never seen; the BLAKE3 hash is the content identity and
  resolves the same weights wherever they are installed. The name step is the last resort and the
  only one that can pick a different file of the same model. Image recall resolves its main model
  and components by key only; its **LoRAs** resolve by `key`, then by `hash` when one was recorded,
  otherwise by `name` + `base`, and skip any portable identifier that matches more than one install.
- **Media references** (`image_name`, `video_name`) are names in the originating gallery, exactly
  as an image record's `init_image` is. Recall restores everything else and clears media it
  cannot find rather than substituting.
- **Workflow and graph** load into the editor on any install, subject to the same model and
  media resolution.

The [Video Recall API](/development/guides/video-recall-api/) takes its parameters under these
same key names from an external process, with models given by name.

## Evolving the record

1. Add a typed `Optional` field to `CoreMetadataInvocation` under its canonical name, stamp it from
   the graph builder, and read it in the recall mappers.
2. Bump `CORE_METADATA_VERSION`'s minor component. Bump the major only for a rename, removal or
   type change, and add the old spelling to the readers' alias table.
3. Update the tables on this page.
